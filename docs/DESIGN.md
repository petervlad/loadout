# Design

loadout moves agents, skills and knowledge bases between people and AI tools. It never calls a model and holds no AI keys: each person's own tool and subscription do that. The one command that starts an agent, `review` (`review PKG` and `review compare`), does it on the reviewer's machine in the reviewer's own AI tool, never on a server.

`cmd/loadout` builds every service. Commands that need one per run get a factory on `cli.Deps` instead: `NewSyncer` builds the `sync` service around the connector the command resolves, and `OpenRegistry` opens the SQLite database in a `--data` folder with the registry and account services on top, for `serve`, `token`, `namespace`, `member`, `user` and `package`. Its `NewHandler` builds the HTTP handler (with the login pages when configured) only for `serve`. `internal/cli` constructs no service itself.

Dependencies point inwards. The installer knows only the `target.Renderer` interface, the registry only its `Store`, `TokenStore` and `NamespaceStore` interfaces, and `sync` only its `Registry` and `Notifier` interfaces, so a new AI tool, storage backend or notification channel is one new package plus one line of wiring. Every `Store` implementation runs the shared contract suite in `registrytest`, which includes `RunPackageDeleteContract` for `PackageFootprint` and `DeletePackage`.

## Package kinds

A package is an agent, a skill, a knowledge base or a pipeline (`kind:` in `loadout.yaml`). Everything outside two places and the table's hooks is kind-blind: publishing, fetching, layers, tokens, sync, rollback, proposals and the lock all move a package's files and its digest.

- `internal/pack/kinds.go` has one entry per kind: its main file, how its content validates, how a new one is scaffolded, and its size limits.
- `target.Render` turns a package into a `Unit` for one tool: an agent file, or a skill folder. Skills and knowledge bases share the skill layout, so adapters only say where their tool reads skills.

- The table's optional `lint` hook returns `pack.Finding` warnings through `Pack.Lint()`. The agent kind's lint finds an agent that names its successor (`Next: run lime-code-review`, `then run lime-test`, `hand off to lime-dev`) with `agent.Definition.Handoffs`, because handoffs live in pipelines (`docs/adr/0001-handoffs-live-in-pipelines.md`). `loadout publish` and `loadout propose` print the findings after the upload line. They never fail the command, and the registry does not lint, so an older CLI's upload is unchanged.

The table's optional `start`, `needs`, `standalone`, `checkNeeds`, `compatible` and `noReview` hooks say what only some kinds have: a first version other than 0.1.0, packages and agents that must exist, an install that is not on its own, a rule inside one major, and a ban on `review`. Callers read them through methods on `Pack` and `Kind` (see Pipelines).

A new kind is an entry in the table, its content type, and a case in `Render`.

| Kind | Author writes | Installed as |
| --- | --- | --- |
| `agent` | `agent.md` | one agent file per tool |
| `skill` | `SKILL.md`, optional files in folders | `<skills>/<name>/` |
| `kb` | Markdown or text documents, in folders | a skill folder with a generated `SKILL.md` index |
| `pipeline` | `pipeline.yaml`: a template of slots and edges, or a binding of those slots to agents | nothing for a template, one conductor agent per tool for a binding |

A skill's `SKILL.md` may carry fields loadout does not read, from the Agent Skills format or one tool (`allowed-tools`, `metadata`, `compatibility`, `disable-model-invocation`, `argument-hint`). They are kept verbatim and in order after `name`, `description` and `license`, which loadout validates, so installing a skill never loses a setting.

An agent's tools are `read`, `search`, `edit`, `shell`, `web`, `agent` and `skill` (load skills). `skill` is `Skill` in Claude Code. Copilot has no alias for it and loads skills on its own, so it maps to nothing to grant. An agent whose tools all map to nothing still renders `tools: []` for Copilot (no tools), never a missing list, which both tools read as every tool.

Skills live in `~/.claude/skills` and `~/.copilot/skills` for a person, and in a repository's `.claude/skills` for both tools (Copilot reads it too, so a repository holds one copy). A knowledge base is a skill on purpose: tools load only its description at startup and open a document when a task needs it, and no tool needs a feature of its own.

Files may sit in folders, at most 8 deep. `pack.CheckPath` is the one check between a bundle from the network and a path on disk: relative, no `..`, no hidden or odd characters, and no two paths that differ only in case, since macOS and Windows would write them to the same file. Packages hold UTF-8 text only, so every change can be diffed and reviewed. Diagrams are Mermaid (`.mmd`, or a mermaid block in Markdown) or draw.io saved uncompressed (`.drawio`, or a drawio block in Markdown). A compressed `.drawio` is refused with how to fix it. PDFs and images are turned into text and diagrams before publishing, by skills that run in the author's own AI tool. Limits depend on the kind, and count every file, the manifest included:

| Kind | Files | Per file | In all (uncompressed) |
| --- | --- | --- | --- |
| `agent` | 16 | 512 KB | 1 MB |
| `skill`, `kb` | 5,000 | 2 MB | 64 MB |
| `pipeline` | 4 | 64 KB | 128 KB |

An agent is one prompt, so it stays small. Skills and knowledge bases hold reference material, and a team's mirror of a wiki space runs to thousands of documents. `pack.Load` does not know the kind while it walks a folder, so it stops at the largest limits and a wrong folder (a home directory) fails fast. `pack.FromFiles` then applies the kind's own. A bundle is at most 32 MB compressed, and `bundle.Decode` stops at the largest limits while reading, before it buffers an upload in full, so a zip bomb goes no further than 64 MB. Uploads and downloads of a bundle get 10 minutes on the server and in the client (other requests keep their short timeouts), and Caddy accepts request bodies up to 40 MB.

A knowledge base's generated index lists every document up to 150 of them. Above that it lists each top-level folder, and the top-level files, with a document count and a few example titles, and tells the tool to search the folder (Grep, Glob) for the rest, so loading the skill does not flood the tool's context.

The installer works per unit: a closer layer's skill replaces a farther layer's whole folder, never file by file, and a folder emptied by an upgrade or an uninstall is removed. `review compare` renders any kind. A skill or knowledge base runs the plain prompt, so the report shows whether the tool picked it up and what it did with it.

## Pipelines

A pipeline is a package kind for a loop that several agents run in turn (plan, dev, review, test), plus the gates between them. Plan in `docs/plans/pipelines.md`, words in `GLOSSARY.md`, the reason handoffs sit here in `docs/adr/0001-handoffs-live-in-pipelines.md`. The one rule holds: a pipeline is YAML, the conductor is an agent file loadout writes on the person's machine, and the person's own tool runs it. The registry stores, checks and draws the YAML and never starts anything.

**Format.** `pipeline.yaml` has two shapes, parsed by `pipeline.Parse` (strict YAML) into a `*Template` or a `*Binding`. Both or neither shape is refused.

- A template has `start`, `slots` and `edges`. A slot has a one-line `brief`, `writes` (its file), optional `also` files that are never checked for a verdict, `reads` (files of other slots or the word `ticket`) and `verdicts`. A verdict is upper-case words with single spaces (`CHANGES REQUESTED`), at most 32 bytes. `QUESTIONS` and `end` are reserved, and `QUESTIONS` is allowed for every slot without being listed. Every verdict has exactly one edge `{from, on, to, via}`, with `via` `gate` or `auto`. `max_rounds` (1 to 10) is allowed only on a back edge, one whose `to` is at or before `from` in the order the slots are written. Limits: 12 slots, 8 verdicts per slot, 64 edges, a `brief` of 500 bytes, file names of one segment that are unique across slots and compared without case.
- A binding has `uses: LAYER/NAME@MAJOR` (a major only), `bind` (slot to agent name), `work_folder`, an optional `model` hint and an optional `gate` list of `{from, on}` pairs. There is no field that makes an edge automatic, so a team can turn `auto` into `gate` and never the other way.
- Fields for topic-dependent slots and nested pipelines are not in the format. They are unknown fields today and refused, so they arrive as a new major of the format, not as a silent change.
- `internal/pipeline` imports no other loadout package that does I/O and not `internal/pack` (pack imports it), so it keeps its own file-name check with `pack.CheckPath`'s alphabet. `Ref{Layer, Name, Major}` stands in for a package id plus a major. `Bind(binding, template)` returns an immutable `*Bound` or lists every problem. `Compatible(prev, next)` accepts a change when the slots and the verdicts per slot are the same. `Mermaid` draws a template or a bound pipeline (gate edges dashed, automatic solid, back edges labelled with their rounds). `Scaffold` and `ScaffoldTemplate` write a binding with empty slots (the template's edges as comments) and the example template.

**The conductor.** `(*Bound).Conductor(name, Starter)` builds the agent's name, description, model hint and prompt from an embedded `conductor.md.tmpl`. It is a property of the pipeline, so the text is shared by every tool, and the few words that differ per tool come from `Starter.StartAgent(agent)`. The prompt is a numbered list of rules:

1. Start: ask for the ticket key if it is missing and find the run folder `<work_folder>/<TICKET>-*`. A new one is named by the first agent, with the slug from the ticket's title (the conductor may not be able to read the tracker, and a slug from the person's words named a pilot run `-run`).
2. Replay: read every slot file in the run folder, take the first round of the start slot, follow the edge of each round's `Verdict:` line, and stop where a slot has no round left. A `QUESTIONS` round follows no edge. Nothing is stored apart from the files, so a person who edits one changes where the run stands.
3. The fixed `State:` line, printed in the same message as the call that starts an agent, also after an automatic edge, and before every `GATE:` or `STOP:` line. Prose about the inferred state was skipped by the models, a fixed line was not. A rule stated once was still skipped where no person spoke in between, so the rule lists each moment.
4. Start a slot's agent by name with the run folder, the files to read, the file to append a `## Round N` section to, the allowed verdicts, the rule to end with one `Verdict: WORD` line, the person's notes from the last gate, and never the name of another slot.
5. Check the slot's file yourself: it exists and its last line is an allowed verdict, else `STOP:` and no edge.
6. Questions: show them, `GATE:`, and start the same agent again with the answers. Resuming a subagent is not used, because the planner's file holds its earlier questions.
7. Gates stop with a `GATE:` line and wait for `go`. Automatic edges go on.
8. Round caps: an edge that was followed `max_rounds` times already becomes a gate that states both positions.
9. Never edit, never start an unlisted agent, never skip a gate.

`Bound.Allowed(defs)` names the agents the conductor may start (the Claude Code `Agent(a, b, ...)` list: a subagent can only start agents on the conductor's list, so a bound agent that delegates needs its helpers on it) and `Bound.StartShell(defs)` says whether the start slot's agent has a shell tool.

**Rendering.** `target.Render` has one case for the kind (`target/pipeline.go`). `RenderOptions.Requires` holds the template release and `RenderOptions.Agents` the bound agents' definitions, both resolved by the caller. A template is not standalone, so rendering it returns an error wrapping `target.ErrNotStandalone`. A tool opts in to conductors with optional interfaces on its adapter, so a new tool is one method away: `Delegator` (`StartAgent`, required), `AgentLimiter` (`RenderLimited`, Claude Code writes `Agent(a, b, ...)` or plain `Agent`) and `FolderMaker` (`EditCreatesFolders`, Claude Code's edit tool makes folders, Copilot's does not). A tool without `FolderMaker` whose start slot's agent has no shell tool gets a warning on `Unit.Warnings`. The conductor's name is `<team>-<name>` of the binding, and the model hint is `balanced` unless the binding says otherwise, resolved with `Choose` as for any agent. Golden files are `internal/target/testdata/conductor-*.golden.md`.

**The kind table's hooks.** Besides `parse`, `scaffold` and `limits`, an entry may carry `start` (the version a new package begins at, a pipeline's is 1.0.0 because `uses` names majors from 1), `needs` (what must exist: templates at a major and agent names), `standalone` (false for a template, with a one-sentence reason), `checkNeeds` (the package against the releases it needs: `pipeline.Bind` plus the guard that the conductor's name is not a bound agent's), `compatible` (the rule inside one major), `noReview` and `lint`. Callers read them through `Pack.Needs`, `Pack.Standalone`, `Pack.CheckNeeds`, `pack.Compatible`, `Pack.Lint`, `Kind.HasNeeds`, `Kind.ChecksCompatibility` and `Kind.CanRunInReview`, so the registry, install, sync and review never switch on the kind.

**Registry checks.** `registry/needs.go` holds one `checker` that `Service.Publish` and `ProposalService.Propose` call after the bundle decodes and the permission check passes, before the version-conflict check. The view is the package's namespace chain (`ProposalService` gets it through `WithNamespaces`). It refuses, with every sentence in one `ErrInvalid`:

- A required template whose layer is not in the chain, that has no release in the named major, or that is not a template.
- A binding that `pipeline.Bind` refuses against the highest release of that major (an unbound slot, an unknown slot, a gate on an edge the template does not have).
- An agent name that no agent package in the chain publishes (a sibling team's agent does not count).
- A conductor named like a bound agent.
- A change inside a major that `Compatible` refuses (a slot added, removed or renamed, a verdict added or removed), with "That is a major change: publish N.0.0". The comparison is with the highest release of the same major, so inside 0.x every change counts.

Approving a proposal does not check again. Releases are immutable and packages are never deleted, so what the checks read cannot disappear, except in a registry restored from an older backup. No `Store` method was added: the checks use `Releases`, `Release` and `Packages`.

**Install.** `install.Options` carries `Requires` and `Agents`. `Install` refuses a template with its reason, `installAll` skips it with one line and installs every package that needs agents after all the others, because a team's binding may bind an agent from a farther layer. After an install, `Result.Warnings` holds the render warnings followed by one per needed agent that has no entry in the scope. `withNeeds` (`internal/cli/needs.go`) resolves the requirements (`release.Resolve`, the highest release of the major, through the package's view) and the bound agents (the closest layer's agent of that name) for `install`, `install --all`, a folder install of a binding and `rollback`. `Merge` refuses a package that needs another (`install.ErrMergeGenerated`). `status` prints "lime/dev-loop uses acme/dev-loop@1.0.0". `loadout review` refuses a pipeline (`review.CheckRunnable`, before it prints anything) and `reviewplan` leaves pipelines out of the context.

**Side files.** Two records live next to files that older CLIs decode strictly, because a field they do not know makes them call the file damaged, and `MinimumCLI` only warns:

- `lock.Entry.Requires` records the template release a conductor was rendered from (id, version, digest). It is not a field of `lock.yaml`. `lock.Store` keeps it in `lock.requires.yaml` next to the lock (strict YAML, 0600, keyed by package id and scope as the lock keys entries, written under the same flock just before the lock, read by `Load`, which ignores a damaged or wrong-version file with one warning in the log, since the record only lets `sync` see what to render again). A test decodes a lock written by this build with the v0.1.0 `Entry` shape. An older CLI never sees or changes the file, and an entry it rewrites keeps working because the key still matches.
- `syncstate.Behind.Template` (the template release a conductor is behind) is kept in `syncstate.templates.yaml` beside `syncstate.yaml` for the same reason, and because the older session hooks read the state on every start. It is written before the state under the same lock, and a damaged or wrong-version file is ignored with one warning. A test decodes a state written by this build with v0.1.0's `Behind`.

**Sync.** A conductor follows its template like the team's model table (`update.Service.checkTemplate`, `checkRender`). `update.Registry.Releases` lists a package's releases with their kind and `Kind.HasNeeds` says which installs to compare. For each recorded requirement the highest release in the pinned major is looked up. A newer one makes the conductor stale: under `auto` it is rendered again (`pipeline template updated`), under `notify` it is reported (`pipeline template changed`, held by edits like any update), under `pin` nothing happens. A higher major and a vanished pinned major are only lines under the table (`Result.Notes`), never a held state. A conductor with no recorded requirement (the side file was lost) counts as stale and is rendered again, which records the template. `update.Registry.Needs` resolves the template and the bound agents for every render sync does, so a new version of the binding installs with its template as `install` does. The cost is one extra `Releases` call per conductor.

**Web.** The packages list gets a Pipelines tab from `pack.Kinds()`. A pipeline's page draws its diagram through the usual diagram frame (`draw/pipeline.yaml?pipeline=1`, in `ui_pipeline.go`) and lists its slots, its edges and, for a binding, its bound agents linked to their pages with a warning for an unbound slot or an agent the page's layers do not publish. See Web pages and `docs/UI.md`.

**Old CLIs.** `server.MinimumCLI` stays unset, so the registry does not tell older CLIs to update. An older CLI fails the one pipeline in `install --all` with "kind pipeline is not supported" and installs the rest. `CHANGES.md` says so. The release that ships pipelines may raise it to itself.

## Built-in skills

loadout ships four skills that teach a person's AI agent to use it (`loadout-setup`, `loadout-author`, `loadout-review`, `loadout-admin`, plan in `docs/plans/builtin-skills.md`). Their files live in `internal/builtin/skills/` and are embedded with `embed.FS`, so the text always belongs to the CLI that installs it. They are files the person's own tool reads. Nothing runs a model.

- **Normal packages.** `builtin.Packs` turns each folder into a `*pack.Pack` of kind `skill` with a generated manifest: id `loadout/NAME` (the skill name must equal the package name, and the folder is `<skills>/NAME`), the skill's own description, and the CLI version as the package version (the release it is or was built after, `buildinfo.Parse`: `v1.4.0-3-gabc` and a Go pseudo-version after 1.4.0 are 1.4.0, a build without a release version is 0.0.1). They go through the normal installer at user scope, so `status`, `uninstall`, `policy` and the "never overwrite an edit" rule apply unchanged.
- **Lock identity.** Their entries record `source: builtin` and no remote. The registry pass of `sync` skips entries without a remote. The built-in pass touches only entries whose source is `builtin`, so a registry namespace that happens to be called `loadout` is never mistaken for them (such an entry is reported and left alone).
- **Wish and opt-out.** `~/.loadout/builtin.yaml` (strict YAML, 0600, apart from the lock so older CLIs still read the lock) holds `wanted` (set by `login` and `setup --skills`) and `declined` (skills the person uninstalled). `builtin.Service` is built in `cmd/loadout` and reaches the commands through `cli.Deps.Builtins`. It owns small `Installer` and `Detector` interfaces.
- **Ensure** (after `login`, and on every `sync`): nothing unless wanted. A skill is installed for the tools `detect` finds when it is missing, when the embedded digest differs from the lock (a new CLI), or when a tool appeared that it lacks. An up-to-date install is not touched, so an edited `SKILL.md` never blocks or nags until there is new text, and then the installer's conflict check keeps it ("kept your own ..."). Declined, pinned and registry-owned entries are skipped. No marker folder (`detect.ErrNoTool`) writes nothing and creates no folder. Login prints one line saying so, and the recorded wish lets a later `sync` install once a folder appears. A failure only warns: the sign-in or sync stands.
- **`setup --skills [--target T] [--force]`** clears `declined`, sets `wanted` and installs every skill now. `--target` may create the tool's folder because the person asked for it.
- **Sets.** `builtin.Sets()` is a table of `Set` values: the **everyday** set (the four skills above, `Auto`, folder `skills/`) and the **host** set (`loadout-host-setup`, `loadout-host-provision`, folder `host/`, not `Auto`), each with its order and an optional `assets` function that adds files to a skill at pack time (the host set copies the deploy files from `deploy.FS` into the provision skill under `assets/`, and `loadout.env.example` into the setup skill, so `deploy/` stays the only copy). `Packs` and `Names` mean the everyday set (the `/skills` pages and login are unchanged). `PacksOf(set, version)` builds any set. `Service.apply` has one rule per pack: it is considered when its set was asked for in this run (`SetupSets`), when its set is `Auto` and the person wants it, or when its set is not `Auto` and the lock already has it. So `sync` updates installed host skills and never adds them, `setup --host-skills` does not set `wanted` (login and sync do not start adding the everyday skills for it), and `setup --skills` leaves host skills to the normal update. `IsBuiltin`, `Decline` and `uninstall` cover every set. `SetOf` tells the hint which flag brings a skill back. `builtin.yaml` has no new field, so older CLIs read it as before and ignore a host skill's lock entry (source `builtin`, no remote).
- **`setup --host-skills [--target T] [--force]`** installs the host set the same way as `--skills` does the everyday one. It may be combined with `--skills`. `--force` replaces an edit only in the sets named in that run.
- **Honesty.** `internal/cli/builtin_skills_test.go` runs over every set and extracts every `loadout ...` command from the skills' code spans and blocks and walks the cobra tree: a subcommand or flag that does not exist on the command it is given to fails `make check`, as does a `--flag` in the prose that no command has. `internal/builtin` tests lint the frontmatter by building the packs, require the guardrails in every skill, and refuse em-dashes.
- **Host skills: `loadout-host-provision`.** Files in `internal/builtin/host/loadout-host-provision/`: `SKILL.md` (guardrails, flow, the provider table), `references/shapes/` (`vm.md`, `container.md`), `references/providers/` (one file per provider: Hetzner, AWS, DigitalOcean, Fly.io, any VPS, a home server or VM), `references/dns.md`, `references/backups.md`, and `assets/`, which `hostAssets` fills from `deploy.FS` at pack time. Every provider file has the same level 2 headings in the same order (Before you start, Create the machine, Firewall, Name, Deploy, Off-host backups, Cost, Tear down), a `Verified how:` line with a date that says whether the recipe was run or only checked against documentation, a `Sources:` list, and a `Shape:` line naming a shape file that exists. Adding a provider is one file and one row in the table. `internal/builtin/recipes_test.go` enforces all of it, that each `SKILL.md` table names every reference and asset file exactly once, the guardrails (no secret asked for, read or printed, no AI key, `serve --check` and `mail test` to verify, ask before cost, DNS and deletion), and that no command prints the settings file. The honesty test also checks `loadout` commands run through `sudo`, `ssh`, `systemd-run` or `fly`, and in the host set only the flags of `loadout` commands (the files show other tools' flags).
- **Host skills: `loadout-host-setup`.** `SKILL.md` (guardrails, the eight steps, the login-mode table, the email provider table), `references/first-admin.md`, `references/simple-login.md`, `references/google.md`, `references/email/` (one file per provider: `ses.md`, `resend.md`, `postmark.md`, `smtp.md`, each with the same headings in order: Account, Sender domain and DNS, SMTP credentials, Values for loadout.env, Limits and sandbox, Cost, plus `Verified how:` and `Sources:`), and `assets/loadout.env.example` from `deploy.FS`. The skill verifies with `loadout serve --check --env-file` (a laptop-side check that prints no secret) and `loadout mail test` run on the host through `systemd-run` with the service's own environment, so the agent never reads the settings file. Secrets are typed by the person into the file or into `loadout user password`, which needs a terminal (`ssh -t`). The first admin is `admin grant` plus sign-up (email codes), or in simple login the admin `serve` creates itself (see Simple login) and `user password` for further ones.

## Registry

- One namespace per token. A token is `read` or `publish`. It reads its own namespace and every ancestor, and publishes only to its own (see Layers).
- Tokens are random 256-bit secrets shown once. The server stores only their SHA-256.
- Versions are immutable and must increase. A package is identified by its content digest, which the client re-checks after every download.
- A release records who published it (`Release.PublishedBy`, an `Actor`, `published_by` on the wire): the principal of a direct publish (a machine token counts as its maker), or the approver of a release from a proposal, set in the approval's transaction. Direct publishes from before migration 0014 have none, and the CLI and pages then show the version alone.
- Every response to a request with a valid token, errors and health included, may carry `X-Loadout-CLI-Latest` (the release the registry was built from, only when its build is exactly a clean tag) and `X-Loadout-CLI-Minimum` (`server.MinimumCLI`, none so far), set by `server.WithCLI` in `auth` right after the token checks out. Anonymous callers get neither, as with health's version. See CLI updates.
- **Deleting a package** (plan in `docs/plans/package-delete.md`). A package has no row of its own: it is the pair `(team, name)` in `releases` and `proposals`, with `proposal_reviews` and `proposal_prompts` under the proposals and the text `team/name` in `namespaces.course`. `Store.PackageFootprint` reads what is there (`registry.PackageFootprint`: releases lowest first, the newest one's kind, proposal, review and prompt counts, the ids of open proposals oldest first, the namespaces that use it as their course) and `Store.DeletePackage` removes it in one transaction (prompts, reviews, proposals, releases, then the course cleared) and returns what it removed. No release and no proposal is `ErrNotFound`, and a package that only ever had proposals is deleted like any other. Open proposals go with it: only the author withdraws and only a teammate's publish token rejects, so the operator could not close them, and a dead package with a forgotten open proposal would be undeletable. Who deletes (plans `docs/plans/package-delete.md` and `docs/plans/package-delete-ui.md`): the operator on the host (`loadout package delete TEAM/NAME --data DIR [--yes] [--reason T]`: a dry run unless `--yes`, then the counts it really removed), an admin on the web at once (`Access.CanDeletePackage` is `Role == RoleAdmin`), and everyone else through a deletion request that a second person approves (below). Owners, maintainers, members and every token get `ErrForbidden` from the direct path: over HTTP the rule is the one for deleting namespaces. `account.Service.PackageFootprint` and `DeletePackage` share `mayDeletePackage`, which runs before any lookup so a refused person learns nothing about whether the package exists, and the footprint is refused like the delete since its counts cross namespaces. A direct delete needs a reason (`ErrInvalid` before any copy) and leaves a record (below). For a person, a copy of the database comes first (`account.Options.Snapshots`, `Take(ctx, "before-delete-TEAM-NAME")`, implemented by `internal/snapshot.Dir` over `sqlitestore.Store.SnapshotTo`, which is SQLite's `VACUUM INTO`: a read in WAL mode, so publishes go on, written 0600 into `LOADOUT_BACKUP_DIR` as `before-delete-TEAM-NAME-<UTC time>.db`). Without that folder, or when the copy fails (`account.ErrBackupFailed`), nothing is deleted and the web delete is off: `cmd/loadout` sets `web.UI.Deletes` only when the folder is usable. The operator takes no copy (the deploy skill backs up by hand). One direct delete runs at a time (`Service.deleteMu`, and `DeletionService.mu` for approvals), a missing package returns `ErrNotFound` before a copy is taken, and the success writes the log line "package deleted on the web" with the user id, the backup file and the counts, and the `deletions` row below: together they are the audit record. `loadout-backup.sh` removes `before-delete-*.db` after `KEEP_DAYS` like the nightly archives, and the unit lists the folder in `ReadWritePaths`. Tokens, memberships, model tiers and wiki revisions belong to namespaces and stay. `seq` is AUTOINCREMENT, so a later publish under the same name never reuses a seq and `Changes` clients never see it step back. There is no tombstone and no soft delete: the name is free at once, at any version, and the only undo is restoring a backup. Machines that have it installed are told by `sync` (see Updates held back by edits, "Gone").
- **Deletion requests** (plan in `docs/plans/package-delete-ui.md`, phase 2). A request to delete a package is reviewed like a proposal but is not one, so it has its own table (migration 0016, `deletions`): a proposal has a version, a digest and a bundle, none of which mean anything here, and `DeletePackage` removes every proposal of the package, which would delete the request's own record. A row outlives its package: id (`del-` and twelve hex digits, so the proposals' `idPattern`, which refuses a hyphen, gives an older CLI a clean 400), package, required reason, the package's newest release when asked (`Newest`), author, `status` (`open`, `approved`, `rejected`, `withdrawn`, `gone`), who decided and when, the note, `self_approved`, and `removed`, the counts and versions that went, as JSON of its own shape. A partial unique index allows one open request per package (`ErrExists`, 409 `exists`). `registry.DeletionStore` has `CreateDeletion`, `Deletion`, `Deletions`, `DecideDeletion` (reject, withdraw), `ApproveDeletion` (checks the newest release is `Decision.Latest`, deletes the package and closes the request in one transaction, `ErrStale` otherwise) and `RecordDeletion`. Both stores pass one contract suite (`registrytest.RunDeletionContract`). `Store.DeletePackage(ctx, id, at)` shares `deletePackageTx` with them and closes the package's open requests as `gone` at `at`, and `PackageFootprint.Deletions` lists the open ones. `registry.DeletionService` follows `ProposalService`: any person who reads the package's namespace may ask (`Propose`, a reason of at most `MaxNoteSize`, never a machine token), a publish token of the namespace that is not the author's approves or rejects, only the author withdraws, and an owner of the namespace may approve their own with `ApproveInput.AsOwner` and a note, recorded as `SelfApproved` and shown as "Deleted without review". The four-eyes helpers (`checkDecider`, `selfError`, `checkOwnApproval`) take a `subject` (id, team, author, noun) that both services build, so the rules are one code. Approval refuses without a `Snapshots` (`ErrForbidden` naming `LOADOUT_BACKUP_DIR`), refuses with `ErrBehind` (409 `behind`, no copy taken) when a release came out after the request (it was asked about something else: withdraw and ask again), takes the copy named `before-delete-TEAM-NAME` (`ErrBackupFailed` deletes nothing and leaves the request open), then `ApproveDeletion`. Every delete that does not go through review leaves a record by `DeletionService.RecordDelete`, which `account.Options.Deletions` calls instead of `registry.Service.DeletePackage`: an approved, self-approved row with the deleter and the reason, written in the transaction that deletes (the operator's is "operator" with the reason it gave, default "Deleted on the registry host."). `GET`/`POST /v1/deletions` (`internal/server/deletions.go`, `server.WithDeletions`, the list is the principal's namespace or `?team=`, status default `open`, `any` for all, `GET /{id}` adds `latest` and `stale` for an open one) and `approve|reject|withdraw` under `/v1/deletions/{id}/`. The CLI routes ids that start `del-` in `review list|show|approve|reject|withdraw` and refuses `compare` and `report` for them. `loadout propose delete TEAM/NAME --reason T` asks (a package folder that is itself named `delete` is written `./delete`).
- Uploads are capped at the package limits above (32 MB compressed, the kind's file count and sizes), regular files only.

## Layers

A package id is still `namespace/name`, but a namespace can have a parent. A project such as `acme` (kind `project`) can sit above teams `payments` and `mobile` and hold what they all share, for example `acme/python-standards`: the project is their L0, each team an L1.

- A token reads its own namespace and every ancestor, closest first (`GET /v1/layers`). It publishes only to its own, so project maintainers get a publish token on the project and team tokens can never publish to it. Siblings and children are invisible.
- Packages and changes cover all of a token's layers. Seq is global, so changes are each layer's changes merged by seq.
- Namespaces are created on the registry host (`loadout namespace create NAME --parent P --kind team|project`). The parent must exist, so a cycle cannot form, and a chain is at most 4 layers. Every namespace has two layers at most: a project has no parent and every team is in a project, on the web, with `--remote` and on the host alike. `token create` needs the team to exist. Teams made before this rule may still have no project. The pages label by kind, projects L0 and teams L1. New namespaces made by people (web, `--remote`, or on the host) follow two layers: a project has no parent and every team is in a project. The pages label by kind, projects L0 and teams L1, so a legacy root team still shows as L1.

Two layers can ship an agent with the same name, which renders to the same file (`.claude/agents/planner.md`). The closer layer wins:

- Every install records its depth in the lock (0 for the token's own namespace and for folders, 1 for the parent, ...).
- A closer package takes a farther package's file over. The farther entry keeps the path as `shadowed` with the owner, so `status` shows "shadowed by payments/planner" instead of a missing or modified file.
- A farther package whose files a closer one owns writes nothing for them and reports "shadowed by payments/planner", not an error. `sync` leaves a fully shadowed install alone and updates a partly shadowed one at its recorded depth, so a project update never clobbers a team's file.
- Same depth, different package: still a conflict that `--force` cannot override. A takeover never overwrites an edited file without `--force`.
- Uninstalling the closer package names the shadowed ones. Installing them again restores their files.

## Model tiers

An agent names a hint (`fast`, `balanced`, `deep`), never a vendor model. A namespace keeps a small table (plan in `docs/plans/model-tiers.md`): per tool (a target name) and hint, a model in the tool's own words and an optional reasoning effort (`low` to `max`). loadout only writes these values into agent files on the user's machine, so the one rule holds.

- `tier.Table` is immutable and built only by `tier.New`, which checks each value loosely because names change often: a model is 1 to 80 printable runes without spaces at either end (YAML marshalling quotes it, so no value can break the frontmatter), an effort is one of the five levels, a tool follows `ident` rules and a table names at most 8 tools. The registry accepts tools it does not know. The CLI and the web page offer only the installer's adapters. `Digest` is empty for the empty table.
- Inheritance is per value, not per cell: `tier.Stack` holds the tables of a view's chain, closest first, and `Resolve` lets a team's model or effort win over the project's one by one, so a team can raise an effort and keep the project's model. `Origin` names the namespace each value comes from, for the CLI's FROM column and the page's placeholders.
- `target.Render` resolves one `tier.Choice` per tool and hands it to `RenderAgent`: nothing for an agent without a hint, else the table's values, else the adapter's `DefaultModel` (the optional `target.ModelDefaults`, Claude Code's haiku, sonnet, opus, Copilot has none). Adapters never see the table. Claude Code writes `model` and `effort`. Copilot writes the picker name as `model: "Name (copilot)"` for VS Code (kept when it already ends in `(vendor)`) and `models: [id]` for Copilot CLI (lower case, spaces as hyphens, vendor suffix dropped), and the effort as `reasoning-effort`. With an empty table both write byte for byte what they wrote before (golden files). Skills and knowledge bases ignore the table.
- Maintainers of the namespace, owners (of it or a project above) and admins change a namespace's own table (`account.Service.SetModelTiers`, `Access.CanSetTiers`). Every reader of the namespace reads it over the API, which `sync` needs. `GET /v1/tiers` returns the resolved table of the request's view with each value's origin and the digest, for any token including machine tokens. `PUT /v1/namespaces/{ns}/tiers` replaces the namespace's own cells (full replace, login tokens only). The CLI edits with read, apply, put. An older registry answers 404, which means the empty table.
- `lock.Entry.Models` records the digest of the table an install rendered with. Older entries have none, which equals the empty table. The installer's "already installed" check also compares the freshly rendered file hashes, so a new model is never mistaken for unchanged, and a table change that does not touch the package only updates the entry. `sync` fetches the table once per source (a view the person lost answers 403, so it falls back to the package's own namespace, as other single-package requests do). An up-to-date install whose digest differs follows its policy: `auto` fetches the same version and installs it again (`OutcomeRerendered`, "model settings applied", edited files block it), `notify` asks `Installer.Rerenders` and reports `OutcomeModelsChanged` only when a file would change (otherwise it records the digest silently), `pin` does nothing. A failure to read the table fails that source's installs, since updating without it would write the built-in models over the team's.
- `review` renders both versions and the context with the reviewer's resolved table. `--model` is still passed per run and wins.
- Folder installs use the empty table.

## Teams

Which registry holds a team's agents (a LAN box, an on-prem server, the cloud) is the team's choice, so users never pick one.

- `token create --invite --url URL` prints an invite: `ldi_` plus unpadded base64url of `{"v":1,"url","namespace","token","role"}` (`role` is optional and only shown). It carries the token, so it is read only from stdin, never logged, never written to `config.yaml`, and `invite.Invite` redacts the token in `String` and `LogValue`. An unknown `v` is a version error, anything else malformed is refused without echoing the input.
- `team join` checks the registry and the token like `remote add`, adds a remote named after the host (`registry-example-com`, then `-2`), stores the token in `credentials.yaml` and records a binding `namespace -> remote` in `config.yaml`. A remote with the same URL is reused when it has no token, the same token, or only this team's bindings. Otherwise the new token gets its own remote, so each stored token belongs to one team.
- If the registry serves `GET /v1/layers`, every ancestor namespace is bound to the same remote too, recording which joined namespace brought it in (`via`). A 404 means an older registry without layers. An ancestor already bound to another remote is left there.
- A command given a package id picks the registry in this order: `--remote`, the namespace's binding, the remote the install came from (`sync`, `diff`, `rollback`), then the default remote. When bindings exist and there are several remotes, an unbound namespace is an error that says to join the team or pass `--remote`. A `config.yaml` without bindings behaves exactly as before.
- `sync` records the resolved remote on every update it installs, so the lock follows a team that moves registries. `list` without `--remote` lists each bound registry in its own group.
- `team leave` removes the binding and the ancestors only it brought in, then removes each remote and token no other binding uses, and warns about agents installed from them.

## Review

A proposal is a pull request for an agent: a candidate version that is not a release until a teammate approves it. Review works the same on a LAN, on-prem or cloud registry.

- `propose` goes to the registry of the package's team. `review` takes `--team` (or the `--package` of `review list`) to pick one, else the default remote.

- `loadout propose` uploads the candidate with the 1 to 20 prompts the author tested it with (4 KiB each) and a note. Any token that reads the package's namespace may propose, so a team can suggest a change to a layer above it (payments proposes to `acme/python-standards`) and only that layer's publishers decide. There is at most one open proposal per package version, and the version must be higher than the latest release.
- Approving needs a publish token of the team that is not the author's (four eyes, by token id). Matching token labels are refused too, but labels are informational: whoever creates tokens picks them, so the token id is the rule. Reject also needs a teammate's publish token. Only the author withdraws.
- Approving and rejecting are a person's decision. A machine token a maintainer made through their account (for CI) can propose, publish and read, but never approve or reject, and four eyes count it as the maintainer who made it, so it cannot propose something its maker then approves. Tokens made on the registry host with `loadout token create` have no maker and still decide as before: that is how a registry without accounts reviews.
- Owners approve their own proposals (plan in `docs/plans/owner-merge.md`), so a small team or an owner alone can release when review is required. It takes an owner through memberships (of the namespace or of a project above, `registry.Owners`, answered by `account.Roles.Owns`, the admin flag left out so a stolen admin token cannot skip review everywhere), signed in as a person (never a machine or host-made token), an explicit step (`review approve ID --as-owner`, `as_owner` in the API, "Approve as owner…" on the web) and a note saying why. `Owns` is asked only on that path. The proposal and the release it becomes record it (`SelfApproved`, and the release's `Proposal` id), written in the approval's one transaction. The CLI, the proposal page, the reviews list and the package page say "without review". An owner could already turn review off, publish and turn it on again without a trace. This makes that one visible step. `AsOwner` on someone else's proposal changes nothing. Direct publish stays refused under `require_review`. The refusal tells an owner to propose and approve as owner. A registry without accounts (no `WithOwners`) keeps four eyes for everyone.
- Approval is one transaction in the store: the version is checked against the latest release again, the release is inserted and the proposal is marked approved, or nothing changes. If someone published in between, approval fails with a version conflict and the author proposes again. An approved version is a normal release, so `sync` and `status` need no changes.
- Proposals live behind their own `ProposalStore` interface (not `Store`), with the same contract suite for SQLite and the in-memory store.
- A request to delete a package follows the same four-eyes rules (see Deletion requests under Registry): a teammate's publish token approves or rejects, never the author's, only the author withdraws, an owner may approve their own as owner with a note. Approving deletes after a copy of the database. It is not a release and `review compare` and `report` do not apply to it.
- **Behind** (plan in `docs/plans/stale-proposals.md`). A proposal records its base, the release it was made from (`registry.Base`, none before the first release, `ProposalInput.Base`, empty meaning the latest release, a given one must be a release). Where it stands is computed when read, never stored: `ProposalService.Standings` reads the latest release of each package of the list's team with one `Store.Packages` call, and `Standing.Behind` (a release after the base) and `Blocks(v)` (a release at or above the proposed version) answer for the CLI, the API (`latest` on `GET /v1/proposals` and `/v1/proposals/{id}`, `api.Proposal.Behind` and `Blocked` for open proposals only) and the pages.
- **Approving over.** A behind proposal is approved only with `ApproveInput.Over` naming the latest release exactly (`review approve --over V`, `over` in the API, "Approve over V…" on the web), recorded as `ApprovedOver`. Otherwise `ErrBehind` (409 `behind`) with a sentence naming both ways out. `Decision.Latest` carries the latest release the service read, and `ApproveProposal` compares it with the package's latest release inside its transaction (`ErrStale`), so nobody approves over a release they never saw. The service turns that into the refusal the approver would have had. A blocked proposal stays `ErrVersionConflict`.
- **Replacing.** `ProposalInput.Replaces` names the caller's own open proposal of the same package (`Actor.same`, so the author's machine token too, anyone else `ErrForbidden`). `ProposalStore.ReplaceProposal` closes the old one as withdrawn ("replaced by ID", `ReplacedBy`) and stores the new one (`Replaces`) in one transaction, old first so the version may be kept. Of racing replaces and approvals one wins. The old one's active prompts come along with their authors and times, given prompts not already there are appended (at most 20 in all, none needed), and reports stay with the old one. Status stays `withdrawn` on the wire for older clients. An older registry refuses `base` or `replaces` by name, and the client proposes again without them. The old proposal then stays open and the CLI says so.
- **Rebase** (`internal/rebase`, built in `cmd/loadout`, `cli.Deps.NewRebaser`). Runs only on the author's machine and never calls a model. `Locate` works out a folder's base: `--base`, the folder's rebase record, the open proposal named or at the folder's version, the release at that version, else the newest release below it (a guess, said so). The proposal replaced is worked out apart from the base. `Rebase` fetches base, latest and the folder (or, with no folder, the proposal's bundle), refuses a kind change, sets one version in all three manifests, and merges per path with a table of cases: a side that did not change takes the other, the same change applies once, both changed is `textdiff.Merge3` (diff3, conflicts marked `<<<<<<<`/`|||||||`/`=======`/`>>>>>>>` with labels such as `yours (proposal ID)`, `base 2.0.0`, `release 3.0.0`, over 5,000 lines a whole-file conflict), and a file deleted on one side and changed on the other is kept and left undecided. Nothing is written until every file has merged. A clean result must be a valid package. Paths pass `pack.CheckPath` and files are written through `os.Root` with `atomicfile`, only package files deleted (hidden files are untouched), and a failure names what was written. The record (`~/.loadout/rebase.yaml`, strict YAML, 0600, per absolute folder path: registry, package, base, onto, replaces, labels, conflicted and undecided paths) gives the next `propose` or `publish` its base and the proposal it replaces.
- **Propose and publish check.** Both call `Locate` before `--bump` and refuse (`rebase.Origin.Refusal`, one sentence apart from the verb) a folder that is behind, and one whose rebase left markers or undecided files (`Unresolved`, cleared by fixing the files, deleting them or `rebase --resolved FILE`). `--base V|latest` overrides. The check is in the CLI only. The registry still checks versions on publish and approval. A successful upload deletes the record.
- Prompts are a list on the registry (plan in `docs/plans/review-from-the-web.md`), and a comparison runs the current list. Anyone who reads the proposal may add one (the same people who may attach a review, so a team below may ask a project proposal its questions). Only the person who added a prompt edits or removes it (`Actor.same`, so another token of the same user counts), with no maintainer override. Open proposals only. At most 20 active prompts of 4 KiB each and 60 rows per proposal, removed ones included, so adding and removing cannot grow the table without end. A removed prompt keeps its row and its number (`registry.Prompt.Seq`), so a stale form never edits or removes a newer prompt, and the last active prompt cannot be removed. The store enforces both limits and the last-prompt rule in its transaction. Prompt texts are untrusted: the registry only stores them, and only a reviewer's own command sends them to their own tool. API: `POST /v1/proposals/{id}/prompts`, `PUT` and `DELETE /v1/proposals/{id}/prompts/{seq}`. `api.Proposal` keeps `prompts` (the active texts, what older CLIs compare with) and adds `prompt_list` (number, text, who added it, when, when edited), absent from older registries. Migration 0011 adds `proposal_prompts` and copies every stored prompt from the old JSON column with `json_each`, credited to the proposal's author at its creation time. The old `proposals.prompts` column is still written with the active texts on every change, so an older loadout after a rollback reads the current list.
- `loadout review PKG` (and its older form `review compare ID`) is the only part that touches AI, and it runs on the reviewer's laptop, started by them. `reviewplan.Planner` picks the two versions: by default the reviewer's installed version (else the latest release) against the newest open proposal (else the latest release). `--from` and `--to` take a version, `latest` or a proposal id. Its registry is a client in the view of the package's own team, so the context is that team's packages and the layers above, the latest release of each, as `install --all` sees them (`--no-context` skips them). `internal/cli` only prints the plan, the warning and the upload line. `cli.Deps.NewPlanner` builds the planner in `cmd/loadout`. `review.Comparer` renders both sides with the normal adapters into two throwaway project folders under distinct names (`current-NAME`, `candidate-NAME`), renders the same context packages beside each, runs the reviewer's own CLI once per prompt per version, and writes a Markdown report. Runs have the tool's full access by default and `--safe` refuses anything that needs approval. Before a full-access run the CLI prints one warning line naming the proposal's author (by the email in their token label) and `--safe`, and a runner's caveat for the mode (Copilot in safe mode) is printed before the run and kept in the report. `review PKG` uploads by default when the version under review is an open proposal (`--no-upload` keeps it local) and names the proposal and the team that will see it. `review compare ID` uploads only with `--upload`. The report (at most 256 KiB, answers shortened to fit) is attached to the proposal, together with the same result as JSON (also at most 256 KiB) so the web page can show the answers side by side. A registry that predates the JSON part gets the Markdown alone. Reports attached without JSON are shown as plain text. The registry never runs an agent and holds no AI keys.
  - Claude Code: `claude -p --agent NAME --output-format json --no-session-persistence --permission-mode bypassPermissions|dontAsk [--settings JSON] [--model M]`, prompt on standard input, working directory = the throwaway folder. `--agent` runs the session as the rendered project subagent. `bypassPermissions` is full access, `dontAsk` (safe) refuses any tool call that would need approval. `--settings` turns off the reviewer's own install of a reviewed skill. The JSON gives the answer, time and tokens.
  - Copilot CLI: `copilot --prompt=TEXT --agent NAME -s [--allow-all] [--model M]`. `--allow-all` in full mode, and in safe mode `COPILOT_ALLOW_ALL` is removed from its environment. It loads `.github/agents` from the working directory and reports no tokens.
  - The runner is an interface. Tests use a fake and never start a real AI tool. `LOADOUT_*` variables are removed from the tool's environment so a registry token never reaches it.

## Wiki

Each project and team can have one wiki page (plan in `docs/plans/wiki-and-settings.md`): text people write and read. The registry stores and renders it. Nothing runs a model.

- **The page.** `wiki.Doc` is built only by `wiki.NewDoc`: format `md` or `mdx`, UTF-8 without NUL, CRLF and lone CR turned into LF, at most 256 KiB. The format comes from a file name with `wiki.FormatOf` (`.md`, `.markdown`, `.mdx`). The CLI checks a file with these rules before it sends it, and the registry again.
- **Rules.** `registry.WikiService` holds them: the namespace's switch must be on (else `ErrNotFound`, "an owner turns it on in Settings"), a note is one line of at most 200 runes, and a save names its base revision. A save whose text and format equal the newest writes nothing. A base older than the newest is a `*registry.StaleError` (`ErrStale`, 409 `stale`), which carries the newest revision so the API sends it in the error body (`api.ErrorBody.Newest`) and the CLI and the page name who saved in between without parsing a message. A base above the newest is `ErrInvalid`. Logs say `wiki saved` with namespace, revision, user id and size, never the text or note.
- **Store.** `WikiStore` is its own interface, like `ProposalStore`, with `RunWikiStoreContract` for SQLite and `MemStore`. `PutWikiRevision` checks the newest and inserts `base + 1` in one transaction, and the primary key refuses a second insert of the same number, so of two saves on one base only one wins. It prunes to the newest 200 in the same transaction. The namespace switch is `NamespaceStore.SetWiki`.
- **Who.** `account.Service` checks and delegates (`Wiki`, `WikiHistory`, `SaveWiki`, `SetWiki` in `account/wiki.go`): readers of the namespace read, `CanEditWiki` saves, `CanSetWiki` switches (see Roles). The history keeps the author's email as it was, so a deleted user stays named. Saves from the registry host are by "the registry host". Without `Options.Wiki` every method is `ErrNotFound`.
- **API** (`server/wiki.go`, with `WithWiki`, on `asUser`): `GET /v1/namespaces/{ns}/wiki?revision=N` (`api.WikiPage`, revision 0 is the empty page), `PUT /v1/namespaces/{ns}/wiki` (`api.WikiSave`, its body cap is `6 x 256 KiB + 16 KiB`, since Go's JSON encoder may write `<`, `>` and `&` as six bytes, the service checks the real size) and `GET /v1/namespaces/{ns}/wiki/revisions`. The switch is `wiki` in `PATCH /v1/namespaces/{ns}`, beside `require_review`. Machine tokens act for nobody and are refused. An older per-namespace login token passes only where `tokenCovers` lets it manage (publish scope, its namespace and below). An older registry answers 404 without an error body, which the CLI reports as a registry that has no wiki yet.
- **CLI.** `loadout wiki show|pull|push|log --team NS` and `loadout namespace set NS --wiki on|off`. `wiki.Syncer` (built in `cmd/loadout`, reached through `cli.Deps.Wiki`) does the work over a consumer-owned `wiki.Remote`. `internal/cli` adapts the client to it. `wiki.Checkouts` records in `~/.loadout/wiki.yaml` (strict YAML, 0600, atomic), per absolute file path, the registry, namespace, revision and digest of the file as loadout last wrote or pushed it. `pull` replaces an existing file only if it matches that digest or already holds the page's text, unless `--force`, and never a symbolic link. `push` takes its base from `--base`, else the file's record for that page, else 0, and records the digest of the file as it is on disk (so CRLF on Windows does not look edited). A stale push leaves the file alone and prints the `pull` and `push --base` that merge it.
- **Course.** A namespace may name a knowledge base its wiki shows as a course (`registry.Namespace.Course`, a `pack.ID`, zero for none, plan in `docs/plans/wiki-course.md`). `registry.Service.SetCourse` refuses (`ErrInvalid`) a package outside the namespace's chain (not every reader of the wiki could read it), one without a release, and one whose newest release is not a `kb`. It stores the id, never a version, so the course follows the newest release. `registry.CourseOf` picks the closest namespace in a chain that sets one, so a team without its own shows its project's, as packages flow down layers. `account.Service.SetCourse` (`account/wiki.go`) needs `CanSetWiki`, the people who turn the wiki on and off, and logs `course set`. `CourseAbove` says what a namespace shows once its own is cleared. The setting is `course` in `PATCH /v1/namespaces/{ns}`, applied before `require_review` and `wiki`, since it is the only one refused for its value. The answer to a clearing PATCH carries `course_above` and `course_from`. An older registry refuses the field by name and the client says it needs a newer loadout. CLI: `loadout namespace set NS --course TEAM/NAME|none`. Lessons are the top-level Markdown files in path order (no manifest field, no index file), titled by `kb.Title`. Folders hold reference material. The box (`web/ui_course.go`) reads the newest release through the page's principal, so the read check runs on every view, keeps only the lesson files in memory (`bundle.Scan` with `course.IsLesson`), and never fails the wiki page: a course it cannot show is left out for readers and replaced by one line for those who may choose another. Any other error is logged at warn and shown as one line.

## Team memory

Plan in `docs/plans/team-memory.md`, words in `GLOSSARY.md`. A namespace can switch on a memory of short typed facts that its members' agents save for each other, served as an MCP server at `/mcp/t/{ns}`. The server stores text, runs SQLite FTS5 and returns text. It calls no model and holds no AI key, so the one rule holds: the calling agent does all the thinking.

- **Where it lives.** `memory.db` beside `registry.db` holds the switch (`memory_spaces`), the tokens (`memory_tokens`), the entries, their versions and links, the FTS index (`entries_fts`, porter stemming) and the purge records. `registry.db` has no memory column. `sqlitestore.OpenMemory` creates the file 0600 with its own `memorymigrations/` folder and `user_version`, and with `secure_delete(ON)` so freed pages are zeroed. `cmd/loadout` opens it in `registryOpener`, builds `memory.Service` (the rules, over `account.Roles` for rights) and `memory.Tokens` once and passes them to the account service (`Options.MemoryTokens`, so signing out everywhere ends memory tokens), the web (`web.UI.Memory`, `web.UI.MemoryTokens`, `web.UI.MemoryChanged`) and the server (`server.WithMemory`). `serverstats` lists both database files. `loadout-backup.sh` copies every `*.db` in the data folder, so `memory.db` is in the nightly archive with no change to the script.
- **Values** (`internal/memory`). `Type` is `feedback`, `project` or `reference`. `user` is not a type, because preferences stay in personal memory. A `Draft` is built only by `NewDraft`, which scans every text field with `secretscan` first, then checks the type, then the limits, so a text that is too long and also holds a key is refused for the key. Every refusal is a `*Refusal` wrapping `registry.ErrInvalid` that names the rule or limit and the position and never holds the text. Limits (`limits.go`): name 64 runes, description 150 runes, both one line, body 4,096 bytes with a hint to use the team docs, 10 links, a note or reason 200 runes, 200 writes per person per rolling 24 hours. `Entry.Unconfirmed(now)` is true when `confirmed_at` is more than six calendar months back, one rule for the index, search, `get` and the web. An update goes through `Change.Revise`, and a `Change` with only `Confirm` writes a version with action `confirm`.
- **Stores.** `memory.Store`, `TokenStore` and `SwitchStore` are owned by `internal/memory`. `memorytest` holds the contract suites and the in-memory stores, and SQLite (`sqlitestore.MemoryStore`) and the in-memory store pass the same suites. Ids are global, so `Move` changes the namespace and keeps the id, author and history. Every write is one transaction: the entry row, one `entry_versions` row with the full snapshot, the links. `Update` takes the version it read and refuses a stale one with `ErrStale` (409). Search sanitizes the query to words (at most 16, no FTS syntax ever reaches SQLite), tries all of them and then any, and ranks with `bm25`. `Purge` deletes the entry (versions and links cascade), writes a `purges` row, optimizes the FTS index and truncates the WAL, so no copy of the text stays in the file. `Store.Insert` and `Update` take an optional `memory.Within(since, max)`: the daily write count and the write then happen in one transaction, so requests that arrive together cannot all pass the limit of 200. Only save and update versions count as writes (a confirm, a retract and a move do not). `Store.RemoveNamespace` and `SwitchStore.Remove` delete a namespace's entries, history, links and switch row, and `account.Service.DeleteNamespace` calls them through `account.Options.MemoryRemover` after the registry deleted the namespace, so a team made later under the same name starts with memory off and no entries (the log line `memory removed with namespace` holds the namespace and counts, never text). An entry carries `EditedBy`, the label of the newest non-confirm version's author when that is not the author. The server and the web show it beside the author.
- **Rights.** `account/memory.go` adds four methods on `Access`. `CanReadMemory` is `CanRead`. `CanWriteMemory(kind)` needs member or above in a team and maintainer or above in a project, and never through a team below (`Access.Below`). `CanModerateMemory` and `CanSetMemory` need maintainer or above, not through a team below, so owners of the project above qualify and the wiki's stricter switch rule (owners) is not reused. Admins get all four. `Roles.MemoryRights` answers `memory.Rights` and gives none at all for an unknown namespace, so a missing team and a team the person is not in look the same. `memory.Service` takes the `memory.Roles` interface it owns.
- **The service.** Methods take a `Caller` (user id and email, from a memory token or a web session) and a namespace. A request for a namespace the person cannot read, or whose switch is off, is `memory.ErrNoMemory`, which wraps `registry.ErrNotFound` and has one fixed sentence ("No team memory here."), so a 404 never says whether the team exists. The readable layers are the namespace and its project, the project only while its own switch is on. `Search`, `Get` (counts a use), `Recent` and `Index` read them. `Save` needs `Write` on the endpoint's namespace and a write left in the day, and runs the duplicate check unless forced. The store returns up to 20 candidates for the words of the name and description, and the service keeps those that hold at least 60 percent of the new name's significant words (three letters or more, not a stopword) in their name or description, at most 5. The rule is in Go so both stores agree. `Update` needs `Write` where the entry lives. `Retract` is for the author and for those who `Moderate`, needs a reason, and is not refused by the day's limit, although the version it writes is counted. `Move` needs `Moderate` on the team and the project's switch on, and no right on the project. `SetEnabled` needs `Switch`. `Spaces` lists the namespaces where the person has rights and the switch is on. `History` serves the web (entry, versions, and whether the person may retract or move). `Inspect` and `Purge` take no `Caller` and check no rights, so only code on the registry host may hold them, through `cli.Registry.Memory`. Logs say `memory saved`, `updated`, `retracted`, `moved` and `purged` with ids, user, version and byte sizes, and a refusal logs the rule, field and position. Never a name, description, body, reason or search text.
- **Secret filter** (`internal/secretscan`). Pure functions, no I/O, linear time (Go's `regexp` does not backtrack, and the request body is capped first). `Scan(field, text)` returns a `Finding` with the rule name, field, line and column, never the match. It rejects and does not redact, since a redacted memory may be wrong and a stored secret ends up in backups. The rules are a table: AWS access key ids and secret keys, JWTs, private key headers, GitHub, Atlassian, Slack and loadout tokens (`ldt_`, `ldm_`), `password`, `passwd`, `pwd` or `secret` assignments, and a high-entropy rule for long mixed-case runs (this also catches Jira and Confluence personal access tokens, which have no prefix). The allowlist is a table beside it: the AWS documentation example keys, pure hex up to 64 characters, UUIDs, `sha256:` and `sha512-` digests, and placeholder passwords such as `***`, `<...>` and `${VAR}`. A false positive is fixed by a row and a test, never by a flag. The same package runs on the laptop in `memory import`. Besides the named key formats it refuses a password in the address of a service (`url-password`, `scheme://user:pass@host`), a quoted key that names a secret (`json-secret-key`, as in `"password": "x"`), and an `api_key`, `apikey` or `token` assignment with a value of 20 or more characters (`api-key-assignment`). An example key is skipped only when the whole span is the example or an assignment of it, never because a longer run contains one. Names, descriptions, notes and reasons also refuse the line and paragraph separators and every Unicode format character (bidirectional controls and zero-width characters), and a body refuses control characters other than newline, tab and carriage return.
- **Memory tokens.** `ldm_` plus 52 base32 characters (256 bits), stored as SHA-256, bound to one person, valid 90 days. `registry.Service.Authenticate` refuses every secret without the `ldt_` prefix, so a memory token gets 401 on every `/v1` route, and an older loadout after a rollback refuses it too. `TestMemoryTokenRefusedEverywhereElse` reads the server's source for its `/v1` patterns and sends an `ldm_` token to each but the three public ones, so a new route cannot be forgotten. `Tokens.Authenticate` checks the prefix, the hash, the expiry and that the person still exists. Membership is checked on every request, so `member remove` takes effect at once. Tokens are made, listed and revoked by an account token only (`server.asAccount`). A machine token acts for nobody, and a login token limited to one team must not make one that reaches every team. `POST /v1/memory/tokens` returns the secret once with `Cache-Control: no-store`. On the laptop the token is in `~/.loadout/memory-credentials.yaml` (`remote.Store.SetMemoryToken`, 0600, strict YAML, atomic, keyed by remote name, apart from `credentials.yaml` so older CLIs keep reading that) or in `LOADOUT_MEMORY_TOKEN`. A client configuration never holds the token. It only runs `loadout mcp --team T`.
- **Routes** (`server/memory.go`, `WithMemory(Memory{Tokens, Switches, PublicURL}, mcp http.Handler)`): `POST|GET /v1/memory/tokens`, `DELETE /v1/memory/tokens/{id}`, `GET /v1/memory/spaces` (the namespaces where the caller has memory rights and the switch is on, each with its endpoint `{public URL}/mcp/t/{ns}`), and `/mcp/t/{ns}` for any method when `mcp` is not nil. The MCP handler authenticates its own bearer, since the registry's auth does not apply to it. `PATCH /v1/namespaces/{ns}` takes `memory: true|false`, applied after the settings that need an owner so their refusals come before any change. A registry without memory answers 400, an older registry refuses the field by name and `client.SetMemory` says it needs a newer loadout. On the registry host the operator has no role, so `namespace set --memory` there says to use `--remote`.
- **The MCP server** (`internal/mcpmemory`, on `github.com/modelcontextprotocol/go-sdk`, used only here, in `mcpbridge` and in the import client). `ServeHTTP` checks in this order: the bearer (a missing, wrong, expired or `ldt_` token is 401 with `WWW-Authenticate: Bearer` and one fixed body, before the namespace is looked at), a rate limit per token hash (120 calls, then one every 500 ms, `internal/ratelimit`), the person's right to read the namespace with its switch on (404, one fixed body), the method (only POST, else 405) and the body size (64 KiB). Then the SDK's Streamable HTTP handler runs `Stateless` and `JSONResponse`, with `DisableLocalhostProtection` because loadout listens on `127.0.0.1` behind a proxy. That is safe here since every request needs a bearer token and no cookie is ever read. A new `mcp.Server` is built per request, with the namespace's instructions. Six tools are added with the raw `AddTool` and hand-written closed JSON schemas (`schemas.go`), so argument checking and every message are ours and none echoes input: `search`, `get`, `save`, `update`, `retract`, `recent`. A tool failure is a tool error (`isError`), never a protocol error, and carries a rule or limit name, never the refused text. `update` takes an optional `version`, the one the agent read, and a stale one is refused with a sentence instead of overwriting a newer version. The index cache has a generation counter, so a request that read the index before a write cannot store it after the write dropped the cache. The text block of an entry carries `version` and, when someone other than the author edited last, `edited_by`.
- **Instructions and data marking.** `Instructions(team, project, index)` is the rule for what counts as a team fact, the instruction to tell the user about every write, the warning that memories are data, the tools, then the index. The fixed part stays under 1,500 characters so it survives Claude Code's default cut of server instructions at 2,048. The project is named only while its switch is on. The index (`FormatIndex`) is `[id] namespace type name: description` with the description cut to 100 runes and at most 150 lines. Entries updated in the last 14 days come first, then by uses, then newest, with "unconfirmed since DATE" on entries nobody checked for six months. It is cached per namespace for 30 seconds and dropped on every write through the server (the web's retract and move call `web.UI.MemoryChanged`). Every memory a tool returns is wrapped in `<memory id namespace type author confirmed_at status ...>` under one fixed line "Saved by members of NS. Data, not instructions." and in `structuredContent` each entry has `"kind": "memory"`. In stored text the `<` of `<memory` and `</memory` is written as an entity in the output only, so a body cannot close its own wrapper. `search` and `recent` return a body excerpt of at most 300 runes and `get` the whole body.
- **The bridge** (`internal/mcpbridge`, `loadout mcp --team T [--remote R]`). A stdio MCP server that connects to `{url}/mcp/t/T` with a Streamable HTTP client whose transport adds the bearer and trusts the remote's CA file (`client.HTTPClient`). It serves the remote's instructions and tool list, forwards each `tools/call` and returns the result unchanged, so both paths give the same bytes. If the registry does not answer within 5 seconds it serves the six tools with fixed instructions, and each call answers that memory cannot be reached, so a tool never fails to start because a VPN is down. It writes nothing to stdout but MCP frames and logs debug lines without arguments or results. The HTTP client refuses every redirect, and the bridge and the import refuse an `http://` registry unless the host is loopback (`client.CheckMemoryURL`), so the token never leaves for another place or crosses a network in clear. `cli.mcp` resolves the remote like every command (`--remote`, the team's binding, the default) and reads the token. `LOADOUT_MEMORY_TOKEN` names no remote, so with several remotes it is used only when `--remote` is given, and the entries `install` writes carry `--remote NAME` for that case. The bridge is built through `Deps.Bridge` in `cmd/loadout`.
- **Client setup** (`internal/mcpsetup`, built in `cmd/loadout`, `cli.Deps.MemorySetup`). `mcpsetup.Service` has the safety rules of `hook.Service`: user scope only, through `os.Root` on the home folder, no symbolic links, `FILE.loadout.bak` once before its first change, a second read before the rename, nothing written when the bytes are the same, and only tools whose marker folder exists. Copilot's entry is a file edit (`target.MCPConfig`, `~/.copilot/mcp-config.json`). Claude Code's is not: `~/.claude.json` is rewritten by Claude Code itself, so `target.MCPCommands` builds the arguments of `claude mcp add-json --scope user` and `claude mcp remove --scope user`, the service runs them with `HOME` set to the home folder it edits, and the file is only read (`.claude.json` in `CLAUDE_CONFIG_DIR` when that is absolute or starts with `~/`, read through `Options.Getenv`, else in the home folder, and the output shows the full path when it is outside the home folder), and only to find loadout's entries (a name starting `loadout-memory-` whose command holds `loadout` and the arguments `mcp` and `--team`, so a server of the person's with a similar name is never touched). The `settings.json` and hook edits still use `~/.claude`. A `claude` that is not on the PATH is a warning. `install` (every form) and `sync` call `Deps.ensureMemory` after their main work: it asks `GET /v1/memory/spaces` of every remote the person is signed in to, marks a 404 (older registry), a 403 (a token limited to one team) and a remote the person is not signed in to as an incomplete listing, and on any other failure changes nothing, so a laptop offline keeps its config. Then `Ensure` adds an entry for each listed team, naming the registry with `--remote` once the person has more than one, and removes the entries of teams no longer listed only when the listing was complete (every registry answered with a list, even an empty one), one output line per change. Failures warn and never fail the command. The wish file `~/.loadout/mcp.yaml` records the tools declined with `loadout setup --no-memory` (which also removes the entries), and `setup --memory` allows them again and adds them now. The memory token each entry needs is made by `memoryTokens` (`cmd/loadout`, a `mcpsetup.TokenEnsurer`) with the login token and stored with its expiry in `memory-credentials.yaml` (`remote.Store.SetMemoryTokenUntil`), when none is stored, its expiry is unknown, or it ends within 14 days. A token is never printed or logged, and `LOADOUT_MEMORY_TOKEN` stands in for the stored one. Claude Code keeps only 2,048 characters of an MCP server's instructions, where the memory index lives, so when an entry is added for a tool with `target.MCPEnv` (Claude Code) the service also sets `env.CLAUDE_CODE_MAX_MCP_DESCRIPTION_LENGTH` to 24000 in `~/.claude/settings.json`, only when that variable is not set, through the same safe edit, and the output says so.
- **Web** (`ui_memory.go`, `ui_memory_tab.go`). The Settings page has a Team memory switch (`POST /t/{ns}/settings/memory`) for those who may set it, and Account has a Memory tokens section (`POST /account/memory-tokens`, shown once on the page that answers, and `/account/memory-tokens/revoke`). Both are left out when `web.UI.Memory` or `web.UI.MemoryTokens` is nil. The Memory tab (`GET /t/{ns}/memory`) is for readers while the switch is on, and every memory route is the usual 404 while it is off (`inMemory`). It has a search form (`?q`, `?type`, `?layer`) and, with no query, **New this week** (the last 7 days). `GET /t/{ns}/memory/{id}` shows the entry, its links and its history, every version with who, when, the action and a text diff from the version before. `POST /t/{ns}/memory/{id}/retract` (a required reason) and `POST .../move` appear as buttons only when `History` says the person may, and the service checks again. `GET /t/{ns}/memory/setup` lists the endpoint, a `curl` test, the bridge command, and an HTTP configuration. Nothing is edited on the web, and entry text is escaped text with its line breaks, never Markdown, since it is untrusted. The UI review is in `docs/UI.md`.
- **Import** (`internal/memimport`, `loadout memory import DIR --team T [--select N,...] [--new]`). `Read` lists the `*.md` files of the folder (not recursive, `MEMORY.md` skipped, at most 256 KB each, opened through `os.Root`), reads `name`, `description` and `type` from the frontmatter and ignores other fields. `type: user` is always skipped. A table of rules pre-selects: `reference` and `project` select, `feedback` does not, and any first-person, "my", "the user prefers" or email text holds an entry back, and each row says why. `secretscan` runs on the laptop first, so an entry with a finding is shown as refused and never sent. `Run` sends the chosen entries through the `Saver` interface, whose one implementation (`MCPSaver`) is an MCP client calling the team's `save` tool, so every check applies. A duplicate is shown and skipped unless `--new`. Without `--select` and without a terminal, the list is printed and nothing is saved.
- **Purge** (`loadout memory purge --id N --data DIR [--yes] [--backups DIR]`, on the host). Without `--yes` it shows the entry's namespace, author, dates and version count and stops. With it, `Service.Purge` removes the entry and its history, logs `memory entry purged` with ids and counts only, and the command lists the nightly archives in the backup folder (`--backups`, else `LOADOUT_BACKUP_DIR`) made since the entry was first saved (`memory.BackupsHolding`). It ends with a reminder that copies made off the machine are not listed and the secret must be rotated. A purge that ended with a busy write-ahead log has already deleted the entry, so running it again for an id that has a `purges` row only repeats the cleanup (`Store.Scrub`) and succeeds. It also says that a running registry keeps the purged name in its index cache for up to 30 seconds.
- **CLI.** `loadout namespace set NS --memory on|off`, `loadout memory token create|list|revoke [--remote R]` (`create` stores the secret and does not print it unless `--show`), `loadout mcp --team T`, `loadout memory import` and `loadout memory purge`, and `loadout setup --memory|--no-memory [--target T]` for the opt-out.

## Login

Login is only about identity: it never runs a model and holds no AI keys. Namespace tokens stay exactly as they are (CI, LAN setups, invites). Accounts sit on top and end in a normal namespace token.

- **Accounts.** A user has an email (unique, trimmed, lowercased), a name, an optional argon2id password hash, an optional Google subject (unique), the time the address was verified, and an admin flag. Users get roles in namespaces (see Roles below), for example `loadout member add --namespace payments --email E --role maintainer`. The person needs no account first. Adding creates one without a password, which they take over by signing up with that address or with Google.
- **Email and password, then a code.** Sign-up takes an email and a password (12 to 128 characters, not one of a small list of common ones, not the email). It mails a 6-digit code and a link. The account is usable, and the password set, only once one of them is confirmed. The pending password is kept on the code, not the user, so an unverified sign-up by someone else never changes the account. Sign-in checks the password and then mails a code. The session starts only after the code or the link. A wrong password, an unknown email and a user without a password get the same answer after the same argon2id work (a dummy hash), and nothing is mailed. A sign-up for an existing account mails the owner a notice instead of a code. Mails go out from a background queue, so the answer never waits for, or reveals, the mail server.
- **Simple login.** `LOADOUT_LOGIN=simple` (`config.Login.Simple`, wired in `cmd/loadout/login.go`) is a mode for a registry with no mail or Google, and a supported one. The sign-in page takes email and password. A right password starts the session at once (`account.Service.SimpleLogin`, no code, no mail). A wrong password, an unknown email and a user without a password give the same `ErrBadLogin` page after the same argon2id work (decoy hash). The per-address and per-email rate limits and the hash cap stay. `web.Config.Simple` routes only `GET` and `POST /auth/login`: sign-up, the code page and Google are 404 and their buttons and links are hidden. No mail queue starts and SMTP and Google settings are ignored. Without the variable nothing changes. The one seeded account is the first admin (`account.Service.EnsureFirstAdmin`, `internal/account/firstadmin.go`): when `loadout serve` starts in simple login with a public URL and the `users` table is completely empty (`account.CountStore`), it creates `admin@loadout.local` (`account.FirstAdminEmail`, the domain needs a dot, so `admin@localhost` is not an address, and `.local` cannot receive mail, which is why email modes skip it), verified and with the admin flag. The password is `LOADOUT_ADMIN_PASSWORD` (checked by `password.Check`, a refused one stops `serve` with a message and creates nothing) or 24 characters from `crypto/rand` (62-letter-and-digit alphabet without look-alikes, no modulo bias). A generated password goes to stderr once in a marked block written straight to the stream, never through the logger, so it is not in the log file or the access log. It is stored only as an argon2id hash. Under systemd stderr is the journal, which keeps it, so the docs tell the operator to change it with `user password`. There is no forced-change mechanism and the registry cannot tell whether it was changed, so the account page shows a reminder to the first admin's address for as long as it exists. Any account at all disables it: existing registries are untouched and deleting the admin does not bring it back until the table is empty again. Everyone else gets a password from the operator with `loadout user password` (below). The log says "simple login is on" and never a password. `loadout login` works unchanged, since the device flow only needs a web session. `loadout user password --email E` (host only, `--data`) sets a password with `account.Service.SetPasswordAsOperator`: the operator actor only, `password.Check` applies, the account is created if missing, the address is marked verified and the user's other sessions end. The password is read from standard input (a terminal asks twice without echo, a pipe gives one line of at most 4x128 bytes) and is never a flag, so it stays out of shell history and process lists.
- **Codes.** Each challenge has an id (in a cookie), a code and a 256-bit link token, both stored as SHA-256 (the code bound to its challenge id). It expires after 15 minutes, allows 5 code attempts (counted atomically before comparing) and is used once (an atomic `used = 0 -> 1`). A link only shows a Continue button. A POST completes it, so mail scanners that open links cannot use them up.
- **Lockout.** Only the newest code of a user and purpose works: issuing one cancels the open ones. Wrong codes are also counted per user and purpose across codes (table `code_failures`, kept a day): after 10 in 24 hours code entry is locked for that user and purpose, and the page says to wait up to a day or use the mailed link, which still works. So asking for new codes never buys new guesses.
- **Sign-up codes.** A sign-up code only sets the password of an unverified account. Completing one for an account that is verified by now is refused. Verifying an address (by code or Google) cancels its open sign-up codes, and setting the password ends the user's other sessions.
- **Google.** Authorization code flow with PKCE (S256), state and nonce, kept in a short-lived cookie. The ID token is verified with go-oidc (signature, issuer, audience, expiry) and the nonce compared. Only `email_verified=true` is accepted. The user is found by Google subject, else by the verified email (and linked), else created. Google sign-in skips the mailed code. The discovery document is fetched on the first sign-in, not at startup.
- **Sessions.** A random 256-bit id in a cookie, stored as SHA-256 with the user and an expiry 30 days out. Sign-out deletes it. "Sign out everywhere" on the account page (a CSRF-checked `POST /account`), or `loadout logout --all` (`DELETE /v1/auth/tokens`), deletes all of the user's sessions and revokes all their login tokens. Cookies are `HttpOnly`, `SameSite=Lax`, `Secure` and `__Host-` prefixed. Only an `http://localhost` public URL (development) drops `Secure` and the prefix.
- **CSRF.** Every POST form carries a token that must equal a random cookie (double submit). A request whose `Origin` is another site, or whose `Sec-Fetch-Site` says cross-site, is refused too.
- **Pages.** Server-rendered with `html/template` from `embed.FS`, one embedded stylesheet and one small same-origin script, and their own `Content-Security-Policy: default-src 'none'; style-src 'self'; script-src 'self'; form-action 'self'; frame-ancestors 'none'; img-src 'self'; base-uri 'none'` (no inline script or style). Every page works without the script. It only adds Copy buttons and small conveniences. The API sets `default-src 'none'; frame-ancestors 'none'` on every `/v1` response itself. Caddy adds that policy only when the upstream sent none. Every response also says `X-Frame-Options: DENY`, except the diagram frame (below). Caddy adds DENY only when loadout sent none.
- **Diagram frames.** A preview page and a wiki page (and only they) add `frame-src 'self'`. Mermaid and the draw.io viewer need inline styles and are a few megabytes of third-party code parsing untrusted text, so they never run on a page: each diagram draws in `/t/{ns}/p/{team}/{name}/{version}/draw/{path}` (a wiki's in `/t/{ns}/wiki/r/{seq}/draw`), a document of its own (`templates/frame/frame.html`) embedded as `<iframe sandbox="allow-scripts">` by `ui.js`. Its source comes from the stored package file or wiki revision on the server (`?block=K` picks the K-th mermaid fence, `?drawio=K` the K-th draw.io fence, `?page=N` the draw.io page), never from the URL. Its response has `Content-Security-Policy: default-src 'none'; script-src {origin}; style-src {origin} 'unsafe-inline'; img-src {origin} data:; font-src {origin} data:; frame-ancestors 'self'; base-uri 'none'; form-action 'none'; sandbox allow-scripts` (the public origin written out, since browsers have differed on `'self'` in a sandboxed document) and `X-Frame-Options: SAMEORIGIN`. So the frame has an opaque origin (no session cookie, nothing of the page), no network, no popups and no forms, also when opened directly. It only tells the page its height (`postMessage` to its own URL's origin). `ui.js` accepts that from its own frames only and clamps it to 120 to 3,000 px. Mermaid runs with `securityLevel: 'strict'` and SVG-text labels, and a diagram's `%%{init}%%` cannot change those. The draw.io viewer gets its settings from script, its resource paths pointed at a path that does not exist, and `dark-mode: light` (draw.io diagrams keep their author's colors on a white canvas in both themes). Neither needs `'unsafe-eval'`. The libraries are vendored by `scripts/vendor.sh` (pinned versions and hashes, checked against a second source) into `internal/web/static/vendor` with their licenses and `VERSIONS`, embedded gzipped (about 2.5 MB of every binary) and served with `Content-Encoding: gzip` and a year of `immutable` caching, since the version is in the path. A test checks `VERSIONS` against the embedded files.
- **Rate limits.** In memory, token buckets per client address (20, then one per 15 s) and per email typed (5, then one per 2 min) on sign-up, sign-in and code entry, per address and per signed-in user on device code lookups, and per address on the device endpoints. A client address is an IPv4 address or an IPv6 /64, since one IPv6 client usually holds a whole /64. A full table (50,000 keys) only drops buckets that have refilled. If none has, new keys are refused, so a flood of keys never resets anyone's limit. They sit behind a one-method interface so they can move to a shared store. Behind Caddy on the same machine the address comes from `X-Real-IP`, trusted only from a loopback peer (`ratelimit.ClientIP`). A proxy that is not on this machine (a container platform, a tunnel, a load balancer) is declared with `ratelimit.Proxies`: `NewProxies(header, trusted)` refuses an empty header, a header that holds a list (`X-Forwarded-For`, `Forwarded`) and any range that covers every address (`/0`), and `Wrap` sets `r.RemoteAddr` to the header's address when the peer is in a trusted range and the header holds exactly one valid address (otherwise the request is untouched), dropping `X-Real-IP` so a loopback client named by the proxy does not make it count again. `ClientIP` and its callers do not change. `cmd/loadout` wraps the whole handler, so the access log sees the client too. Settings: `LOADOUT_TRUSTED_PROXIES` and `LOADOUT_CLIENT_IP_HEADER` (below), unset by default.
- **Password hashing.** At most 4 argon2id hashes (about 19 MiB each) run at once, the decoy hashes included. A request waits up to 2 seconds for a slot and then gets a "busy, try again" page (503).
- **`loadout login` (device flow).** `POST /v1/auth/device {namespace}` returns a device code (the CLI's secret), a user code like `BCDF-GHJK` (consonants only), the page `{public URL}/auth/device` and the poll interval. The CLI prints them, opens the page through a small `Browser` interface (only when it is on the registry's own scheme and host, otherwise it prints the registry's own device page and opens nothing), and polls `POST /v1/auth/device/token` (`authorization_pending`, `slow_down`, `expired`, `denied`, or `approved` with the token). On the page the signed-in person sees the code, the namespace and their role (or picks one of their teams when the CLI named none) and approves. The first poll after approval issues a normal namespace token for their role (see Roles), labelled `<email> via loadout login`, bound to the user id and valid for 90 days (`loadout login` again gets a fresh one). The CLI stores it in `credentials.yaml` and binds the namespace exactly like `team join`. With `--team` the CLI refuses (and revokes) a token for any other namespace. Without it, it shows the namespace and saves the token only after a yes (`--yes` skips the question). Device state is in memory and lasts 15 minutes. One client address may have 5 sign-ins pending, and when 10,000 are pending the oldest unapproved one is dropped to make room.
- **Revocation.** A user-bound token stops working 90 days after it was issued (`tokens.expires_at`, checked at authentication). It is also checked against the user's effective role on every request: no role means 401, a role below maintainer means read (the token's scope is a ceiling, a promoted user runs `loadout login` again to publish). `member remove` and `user delete` also delete the user's tokens. `loadout logout` revokes its token with `DELETE /v1/auth/token` (allowed only for tokens from `loadout login`, since an admin-made token may be shared) and leaves the team like `team leave`.
- **Storage.** Migration 0005 adds `tokens.created_by_user_id` (the maker of a machine token), 0006 `tokens.expires_at` (login tokens issued before get 90 days from the upgrade), 0007 the table `code_failures`, 0010 `proposals.self_approved`, `releases.proposal_id` and `releases.self_approved` (an owner approving their own proposal, old rows had a second person and say nothing about their proposal), 0012 the table `model_tiers` (namespace, tool, hint, model, effort, no rows means built-in defaults, and `DeleteNamespace` removes a namespace's rows in its transaction), 0013 `namespaces.wiki` (off for every namespace that exists) and the table `wiki_revisions` (namespace, seq, format, body, size, author id and email, note, time, primary key namespace and seq, so of two saves on one base only the first inserts and the other is `ErrStale`, the newest 200 are kept, pruned in the save's transaction, and `DeleteNamespace` removes them, a wiki does not keep a namespace from being deleted), 0015 `namespaces.course` (the wiki's course as `team/name`, empty for every namespace that exists, a value that does not parse reads as none and is logged), 0014 `proposals.base_version` (the release a proposal was made from, backfilled as the newest release published before it, `ProposalService.Standings` compares it with the latest release when read, plan in `docs/plans/stale-proposals.md`), `approved_over`, `replaces` and `replaced_by` (empty until approving over a newer release and replacing a proposal land), and `releases.published_by_token_id`, `published_by_label` and `published_by_user_id` (who released it: the publisher, or the approver of a proposal, backfilled from the proposal's decider, empty for older direct publishes). On the wire a proposal carries `base` and, when read, `latest` (`api.Proposal.Behind`), a release `published_by`, and `loadout propose` sends the latest release as `base`. Against a registry that refuses the field by name the client proposes again without it. Users are changed one column at a time (`SetPassword`, `MarkVerified`, `LinkGoogle`, `SetAdmin`), never by writing back a whole row read earlier, so two changes at once cannot undo each other. Migration 0004 adds `tokens.user_id`, `namespaces.require_review`, `proposals.author_user_id` and `decided_by_user_id`, and the tables `users` (with `is_admin`), `memberships` (role `member`, `maintainer` or `owner`), `sessions` (hash, user, times) and `challenges`. Deleting a user cascades to the last three. Existing data needs no change. The store is behind `account.Store` (users, members, sessions, challenges), with the contract suite in `accounttest` run against SQLite and the in-memory store.
- **Logging.** Events carry user ids and namespaces, addresses only redacted (`a***@example.com`). Never passwords, codes, link tokens, session ids or tokens. At startup the server logs which parts of login are on.

### Roles

Four roles decide what a signed-in person may do. Admin is a flag on the user. The other three are stored on a membership of one namespace. Inherited rights are computed from the namespace chain on every check (`account.Resolve`), never stored.

| Role | Where | Install, sync, propose | Publish directly | Approve, reject | Members | Machine tokens | Create teams | Require review | Edit the wiki | Wiki on or off | Delete packages | Namespaces, owners |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| member | a team (or a project) | yes | no | no | no | no | no | no | yes | no | asks | no |
| maintainer | a team | yes | yes, unless review is required | yes, not their own | add and remove members | yes | no | no | yes | no | asks, approves others' | no |
| owner | a project | yes | yes, unless review is required | yes, their own too as owner, with a note, recorded | add and remove members and maintainers | yes | in their project | yes | yes | yes | asks, approves, their own too as owner | no |
| owner of the project above | every team below | as owner | as owner | yes, their own too as owner, with a note, recorded | as owner | yes | no | yes | yes | yes | asks, approves, their own too as owner | no |
| member (any role) of a team below | the project above | yes | no | no | no | no | no | no | no, reads it | no | asks | no |
| admin | everywhere | yes | yes, unless review is required | yes, not their own | everyone, including owners | yes | anywhere | yes | yes | yes | at once on the web, with a reason and a record. Asks, approves | create and delete any namespace |

- A member of a project reads the project (and its ancestors), not the teams below it. Anyone in a team is a member of the projects above it: they read them and may propose to them, but a team maintainer is not a project maintainer. An owner adds that role separately.
- Owner is only given on project namespaces. Maintainers add members. Whoever governs a namespace (an owner of it or of a project above, or an admin) adds maintainers. Admins add owners. Changing or removing someone needs the right to give their current role too.
- `loadout login` issues one account token per registry (namespace `*`, plan in `docs/plans/one-login.md`). It says only who the user is. Each request is narrowed to a namespace (`registry.Service.In`) with the user's role there at that moment: publish for maintainer, owner or admin, read for member. Listings name the namespace in the `X-Loadout-Namespace` header. A request about one package or proposal is narrowed to that package's namespace. `GET /v1/me` lists the account's namespaces for the CLI to bind. Per-namespace login tokens issued before keep working until they expire. Approval (four eyes) needs a publish token of the package's namespace, and must come from neither the author's token nor the author's user: proposals record the user id, and a machine token counts as the user who made it. Machine tokens never approve or reject (see Review).
- The wiki's two permissions live on `account.Access`: `CanEditWiki` is a role of member or above that is not only from a team below (`Access.Below`, set where `Roles.accessOf` raises a team member to member of the project), and `CanSetWiki` is `Governs`. `Below` is read by nothing else, so a caller that misses it gives less, never more.
- `require_review` (per namespace, off by default so nothing changes) refuses every direct publish to that namespace, from any token. Versions go through `propose` and approval. Owners (of it or above) and admins toggle it: `loadout namespace set payments --require-review on`.
- Machine tokens (`ldt_` tokens without a user) keep working exactly as before, read or publish, for CI and LAN setups, and never expire. Maintainers manage their team's machine tokens over HTTP (`loadout token create --remote R --team payments --read`). Such a token records who made it.
- The operator on the registry host (commands with `--data`) may do everything, and alone grants the admin flag: `loadout admin grant|revoke|list --email E`, and deletes a package on the host without a role: `loadout package delete TEAM/NAME` (admins delete at once on the web, everyone else asks, see Deleting a package and Deletion requests). With `--remote`, `member`, `namespace` and `token` commands act as the user signed in on that registry and the rules above apply. A machine token is refused there. Over HTTP an account token carries its user's rights in every namespace (an older per-namespace login token: only with publish scope, in its namespace and those below), and never admin rights: creating root namespaces, giving the owner role and deleting namespaces take an admin signed in on the web, or the operator on the host. The HTTP routes are listed in `internal/server/manage.go`.

On the CLI side one remote holds one registry. `loadout login` binds every lowest namespace from `/v1/me` as a joined team and the projects above as layers, and folds older remotes with the same URL into one (moving their bindings, revoking their tokens). Each request carries a view (`client.In`): the joined team of the package's binding, or the team that brought a layer in (`viewOf` in `internal/cli/connect.go`). `list` and `install --all` read every view and keep each package once. A view that answers 403 (the user left that team) is skipped with a note. A view the user lost refuses only listings. A request about one package or proposal still goes by that package's own namespace, so `sync` keeps working through another team.

Configuration comes from the environment of `loadout serve`. Every part is optional:

| Variable | Effect |
| --- | --- |
| `LOADOUT_PUBLIC_URL` | The address in a browser, e.g. `https://registry.example.com`. Unset: no pages, no device flow. The registry behaves as before |
| `LOADOUT_GOOGLE_CLIENT_ID`, `LOADOUT_GOOGLE_CLIENT_SECRET` | Google sign-in, redirect URI `{public URL}/auth/google/callback`. Unset: no Google button |
| `LOADOUT_SMTP_HOST`, `LOADOUT_SMTP_PORT` (587), `LOADOUT_SMTP_USER`, `LOADOUT_SMTP_PASSWORD`, `LOADOUT_MAIL_FROM` | Email sign-up and sign-in. Unset: they are off (a log line says so) |
| `LOADOUT_DOCS_URL` | Where the pages' Docs, What's new and install links go (`config.Login.DocsURL`: an absolute http or https address with no query or fragment, a trailing slash added). Unset: the project's site (`web.DefaultDocsURL`). For a registry without internet access |
| `LOADOUT_TRUSTED_PROXIES`, `LOADOUT_CLIENT_IP_HEADER` | Which peers may name the client's address, and the header they put it in (`config.Proxies`): comma-separated addresses or ranges (an address alone is a range of one), and one single-address header such as `Fly-Client-IP` or `CF-Connecting-IP`. Both or neither. `serve` refuses `X-Forwarded-For`, `Forwarded` and ranges that cover every address, naming the variable. Unset: only a proxy on this machine, through `X-Real-IP` |
| `LOADOUT_LOGIN=simple` | Simple login (see Login): email and password only, no Google, no sign-up, no mail. Any other value is refused at startup |
| `LOADOUT_ADMIN_PASSWORD` | The password of the first admin that `serve` creates in an empty simple-login registry (`config.Login.AdminPassword`, a secret). Unset: 24 random characters, printed once. Ignored when any account exists |

| `LOADOUT_DEMO=1` | Demo mode (see Demo): simple login with the demo password, a banner on every page, the accounts listed on the sign-in page, mail only logged. `config.Load` refuses it unless `LOADOUT_PUBLIC_URL` is a plain `http` localhost address and no Google or SMTP setting is present, and `serve` refuses a folder that `demo seed` did not make |
| `LOADOUT_HETZNER_TOKEN`, `LOADOUT_HETZNER_SERVER` | The optional Hetzner part of the admins' server page (see Web pages). The token must be a read-only token of the server's project. Unset: the Hetzner and cost panels are not drawn |
| `LOADOUT_HOST_PROVIDER`, `_REGION`, `_SIZE`, `_CONTACT`, `_CONSOLE` | The Host panel of the server page: plain text the operator states (`config.Host`, each trimmed, at most 200 bytes, no control characters, the console must be an absolute https link, or `serve` refuses to start and names the variable). Unset values leave their rows out |
| `LOADOUT_BACKUP_DIR` | Where `loadout-backup.sh` writes, listed read-only on the server page. Also where the registry saves a copy of its database before a package is deleted on the web, directly or after review. Two host commands check this configuration. `config.ParseEnvFile` reads the subset of systemd's `EnvironmentFile` syntax that `deploy/` installs (comments, blank lines, `KEY=VALUE`, one pair of matching quotes, CRLF, later keys win, `export` and a line without `=` are refused) and never runs the file or expands anything. Its errors name the line and the variable, never a value. `config.Unknown` names `LOADOUT_` variables nothing reads, so a typo is reported instead of turning a feature off. `loadout serve --check [--env-file F]` loads the configuration (the file's, with only `HOME` from the process, or the process environment), builds the login parts through the same `buildLoginParts` in `cmd/loadout/login.go` that `serve` uses (public URL, mailer, Google client, no network), prints one line per part (public URL, login mode, email as `smtp via host:port`, `log` or `off`, Google on or off, docs address, proxies, server page facts, unknown variables) and exits 0, or fails naming the variable. Secrets only ever show as on or off. An unknown variable is printed with the other lines and then fails the check (exit 1), since a typo silently turns a feature off. `loadout mail test --to A` builds the same mailer (`cli.Deps.NewMailer`) and sends one message directly, not through the queue, so the SMTP answer comes back to the operator. Log-only, off and simple login are refused with the reason. `mail test` opens nothing. `serve --check` adds a `first admin:` line (`will be created (empty database)`, `exists`, or `off` outside simple login) from `sqlitestore.HasAccounts`, which opens the file read-only, never creates or migrates it, and treats a missing file or table as empty.

The host setup lives in `deploy/` and works on any Debian or Ubuntu machine you can ssh to, or in a container. `prepare.sh` is idempotent (packages, ssh hardening for one admin user and only when that user has a key, ufw, Caddy from its apt repository, the `loadout` user and folders). `cloud-init.yaml` keeps only what must happen before the first login. `deploy.sh` takes the binary from the checkout (`go build`), `LOADOUT_BINARY` (an ELF file) or `LOADOUT_VERSION` (a release archive checked against the release's `checksums.txt` before use), runs `prepare.sh` only with `LOADOUT_PREPARE=1`, installs the static site (`site.caddy` in `/etc/caddy/loadout.d/` and the pages) only when `LOADOUT_SITE_DIR` and `LOADOUT_SITE_DOMAIN` are both set, and sends one quoted script to the host over ssh. On the host it runs `serve --check` with the new binary over the new (or existing) settings file, and `caddy adapt` over the configuration it is about to install, both before anything running is replaced. A failure stops the deploy with the service as it was. The Caddyfile imports `/etc/caddy/loadout.d/*.caddy` first (a global block for a tunnel, or `site.caddy`) and sends `X-Real-IP {client_ip}`. `container/Dockerfile` builds from a release with the same checksum rule.

## Demo

`loadout demo seed --data DIR` writes an invented world (projects `acme` with teams `lime` and `koala` and `globex` with `pear` and `otter`, and seven people at `example.com`) through the same services the registry runs on. `internal/demo` holds the story as tables: `world.go` (memberships, releases, proposals), `memories.go` (team memory, its edits, retractions and moves), `catalog.go` and `build.go` (builders for agents, skills, knowledge bases and pipelines). `internal/demo/content/` keeps the few packages that are easier as real package folders, the dev loop template and the wiki pages. `demo.Seed` takes a `World` of services built by `cmd/loadout/demo.go` over a `demo.Clock` that it moves back five weeks and forward again, so releases, proposals, wiki revisions and memory entries carry dates over the weeks. Nothing is written by SQL, no token or session is left behind, and the accounts get the one password `demo.Password`.

The marker is SQLite's `application_id` in `registry.db` (`sqlitestore.MarkDemo`, `DemoMarked`), set last, so a seed that failed leaves nothing behind (`demo seed` removes the database files it made). `cli.Deps.seedDemo` is the policy: a folder with the marker is left as it is, an empty or missing one is seeded, anything else is refused.

Demo mode is `LOADOUT_DEMO=1`, in the normal binary behind three guards: `config.Login.demo` (localhost `http` public URL, no Google, no SMTP), `registryOpener` (the folder carries the marker) and, for the container, `demo up`, which seeds and then serves. It sets `Simple` and `Dev`, so login, mail and the routes are exactly simple login. `web.Config.Demo` adds the banner to both layouts and the account list to the sign-in page. Nothing else in the pages differs.

`compose.yaml` and `deploy/demo/` run it. The `registry` image is distroless and starts `demo up` on a named volume. The `cli` image is Debian slim with bash and git, shares the registry's network (so the registry is `localhost` there too), and `cli-entrypoint.sh` signs alice in with the demo password, approves `loadout login` for her through the device page and makes her memory token. `scripts/preview/seed.sh` calls `loadout demo seed` for the shared world and adds its screenshot-only extras on top.

## Web pages

With a public URL the registry also serves pages for people (routes in `internal/web/ui.go`), designed with the Apple HIG as reference (see UI.md):

- `/t/{ns}` lists the packages a team reads (its own and the layers above), with the command that installs them on a new machine. Links, not script, filter and order it: `?q=` searches, `?kind=agent|skill|kb|pipeline` and `?layer=NS` filter (each tab counts what it would show with the other filters kept), `?sort=name|kind|updated|releases` orders. Unknown values fall back to the defaults. `/t/{ns}/p/{team}/{name}` shows one package's releases and main file. `?version=V` shows an older release (and says which is the newest). ### Adding a cloud provider

The server page can show the machine as its cloud sees it. The seam is `serverstats.CloudProvider`:

```go
type CloudProvider interface {
	Name() string                                          // "Hetzner", titles the panel
	Summary(ctx context.Context) (CloudSummary, error)     // facts and an optional cost
}
```

`CloudSummary` holds `Facts` (label, value, note and an optional `ok` or `warn` tone) and a `*CloudCost` (currency, total, lines, a note saying where the figures come from). A nil cost leaves the cost panel and tile out. An error's text is shown to the admin as it is, so it is one plain sentence that says what to check and never holds a secret. The provider only reads, bounds its own time and caches, since the page asks on every load.

To add one: write the type (see `internal/hetzner/provider.go`), then a factory in `cmd/loadout` of the form `func(config.Stats, *slog.Logger) (serverstats.CloudProvider, error)` that returns `nil, nil` when its settings are absent, and add it to `cloudFactories()` in `cmd/loadout/cloud.go`. The first factory with settings wins. A provider with its own settings reads them from the environment in its factory. With no provider the page works and has no cloud section.

## Rules that protect users

- An install renders every file and checks every path before writing anything.
- A file loadout did not write, or one edited since, is never overwritten without `--force`. An update it holds back is remembered and reported (sync's next steps, exit code 2 for `auto`) until the person takes it, keeps their version with `pin`, or reverts the edit. `install --merge` takes it and keeps the edit, merging against a base that must hash to what loadout wrote. Conflicts are marked in the file and reported until resolved.
- Files are written atomically and through `os.Root`, so a bad name cannot escape the target folder.
- The lock is written atomically.
- Review runs start in a throwaway folder, with the tool's full access by default (a warning line names whose text runs) and safe mode on request (`--safe`). `LOADOUT_*` variables never reach the tool.

## Logging

- Terminal: human-readable, warn level by default, debug with `-v` or `LOADOUT_LOG=debug`.
- `~/.loadout/loadout.log`: JSON, always debug, rotated at 5 MiB. Every run records its start, its events and its end with duration and error.
- An error is either returned or logged, never both. User-facing errors are printed once by `main`.

## Notifications

`sync` reports updates for `notify` installs through a small interface defined in `internal/update`. On the terminal the sync table is the notification. Pushover is the next implementation:

```go
type Notifier interface {
	Notify(ctx context.Context, n Notification) error
}
```

- `internal/notify/pushover`: set `LOADOUT_PUSHOVER_TOKEN` (your Pushover application token) and `LOADOUT_PUSHOVER_USER` (your user key) and `sync` pushes one message per new version of an install, available or held back. Both come only from the environment, never from a file loadout writes. Run `loadout sync` from cron to get pushes without opening a terminal. A held-back update's message counts the edited files ("You edited 1 file, so loadout kept 1.2.0. Run loadout status."), never names them, so no path leaves the machine.

A newer loadout is pushed from `sync` too, by `cli.AfterRun` (the `sync` command is marked `pushUpdates`): `cliupdate.Service.Push` sends `Status.Push` through the one-method `cliupdate.Pusher`, which `pushover.Notifier.Push` implements (`Notify` sends through it), once per version on its own clock in `cliupdate.yaml`, a failure retried next run. With `LOADOUT_UPDATE_NOTICE=off` only "too old for this registry" is pushed.

**Once per version.** `sync` decides in its loop and tells the notifier after it, in one place (`update.Service.tell`), against what the last sync recorded (`internal/syncstate`): it notifies when the install has no record, a record of another latest version or model digest, a record whose held state changed (an available update that became held is news), or one whose notification failed (`Told` false). A failed notification is logged as a warning, never fails the sync, and is tried again next run.

## Updates held back by edits

Plan in `docs/plans/held-back-updates.md`. loadout never overwrites a file someone edited, so an edit holds an update back. This part makes sure the person keeps hearing about it.

- **Detect.** For `auto`, the installer's `*install.ConflictError` gives every file in the way with its reason (`OutcomeBlocked`, "held back by your edits", a model-only hold has `Latest` equal to the installed version). For `notify` with a newer release or changed models, `sync` asks `Installer.Edited` (hashes of the entry's files, no fetch) and keeps the outcome, with the edited files in `Result.Held`. Pinned and fully shadowed installs are not checked.
- **Remember.** After the loop `sync` writes every checked install in one `Memory.Update` to `~/.loadout/syncstate.yaml` (strict YAML, 0600, atomic, under its own `flock`, user scope saved without its root, as in the lock): `Put` for one behind its registry (version, latest, model digest, files in the way with their reasons, first and last seen, told), `Drop` for one in step, pinned or shadowed. A failed check keeps the old record, so a registry outage forgets nothing. The file is apart from the lock because older loadouts read the lock strictly, and it is a hint only: a damaged file reads as empty for status and is started afresh by the next sync. A failed write is a warning.
- **Built-in skills.** `builtin.Options.Memory` (a one-method interface owned by `builtin`) records a skill kept over an edit (`ActionKept`) with the CLI's version as latest, and drops the record when the skill is in step. Their way out is `setup --skills --force`.
- **Say what to do.** `sync` prints, per install with files in the way, the files grouped by reason (user scope under `~`, project scope in full) and the ways forward: `loadout diff`, `install --force` (only when no file is one `--force` cannot replace, `install.Reason.Blocking`), `policy ... pin`, with `--scope project` and the folder to run them in for a project install. The installer's own "use --force" error is no longer printed for these.
- **Show it, offline.** `internal/notice` is built in `cmd/loadout` from the state store and the installer only (`notice.Files`: `Entries`, `Edited`), so it cannot reach a registry. `List` shows a record only while it is still true: the lock has the install, it is still below `Latest` (or, for a model change, its `Models` digest differs from the recorded one), and for a held update `Edited` still finds a recorded path edited (only those paths are read, so a large knowledge base stays cheap, files in the way that loadout did not write keep holding until the next sync). A held update whose edits were reverted shows as available. An install that caught up, was forced or uninstalled shows nothing, without anyone writing to the state. A damaged state reads as empty. `Filter.Dir` matches a project install when the folder is inside its root (user scope always matches). When only held notices are asked for and nothing is held, the lock is not read at all. `status` prints `List` below its table ("As of the last sync (time):", one `Sentence` per install). `loadout notices` prints the held ones as lines.
- **Session output.** `target.SessionHook` is the optional adapter interface for tools that run a command when a session starts. `SessionOutput(target.SessionMessage{Person, Agent})` gives the tool's JSON: Claude Code `{"systemMessage", "hookSpecificOutput": {"hookEventName": "SessionStart", "additionalContext"}}` (the person sees the first, Claude gets the second), Copilot `{"additionalContext"}` plus the same under `hookSpecificOutput` for VS Code (only the agent sees it). `notice.Message` builds both lines from the held notices, at most three names and "and N more". The agent is asked to mention it once, in one sentence, and never to run `install --force` without asking. `loadout notices --hook claude|copilot` reads at most 64 KiB of hook input within a 1 second deadline, stays silent for sources other than `startup` and `new` (VS Code ignores matchers), lists held notices for the input's `cwd`, and on any error prints nothing and exits 0 (logged at debug).
- **Session hooks** (`internal/hook`, built in `cmd/loadout`, `cli.Deps.Hooks`). `target.SessionHook` also gives each adapter's hook file and how to add or remove loadout's hook in it, as pure functions on bytes: Claude Code's is `~/.claude/settings.json`, where `WithHook` appends one matcher group `{"matcher": "startup", "hooks": [{"type": "command", "command": ..., "timeout": 5}]}` to `hooks.SessionStart` (on Windows the PowerShell form with `"shell": "powershell"`) and recognises its own handler by a command holding `loadout` and `notices --hook claude`, replacing an older one in place. `WithoutHook` removes it, then a matcher group, `SessionStart` and `hooks` only when that emptied them, and nil (delete) when nothing else is left. The edit goes through `internal/jsonedit`, which parses with `encoding/json/jsontext` (so comments, trailing commas, duplicate names and invalid UTF-8 are refused, never repaired), splices the new text in at the siblings' indentation, and keeps every other byte. Removing what it added gives the original bytes back (fuzz tested). Copilot's is a file of loadout's own, `~/.copilot/hooks/loadout.json` (`{"version": 1, "hooks": {"sessionStart": [{"type": "command", "bash", "powershell", "timeoutSec": 5}]}}`), read by Copilot CLI and by VS Code. `hook.Service` writes user scope only (a project's hooks are code everyone who clones it runs), through `os.Root` on the home folder and `atomicfile.WriteIn`. It refuses, with the entry printed to add by hand, when any part of the path is a symbolic link or the adapter refuses the content, keeps `FILE.loadout.bak` once before its first change to a file holding anything of the person's, reads the file again just before the rename and starts over once if it changed, writes nothing when the bytes are the same, and only sets up a tool whose marker folder exists (creating `hooks/` inside `~/.copilot`). The command is bare `loadout` when the PATH finds the running binary, else its quoted absolute path (`os.Executable` and `exec.LookPath`, injected through `externals`). `2>/dev/null || true` (PowerShell: `Get-Command`/`Test-Path` and `exit 0`) keeps a missing or older loadout silent. The wish is `~/.loadout/hooks.yaml` (strict YAML, 0600: `wanted`, `declined`): `login` runs `Ensure` (set up unless declined) and prints one line. `setup --hooks` sets them up and `setup --no-hooks` removes them and records the decline. `sync` never edits a hook or settings file (it runs from cron) and prints one tip when something is held back and neither was chosen. The one exception, when it is wired in (see Team memory), is loadout's own memory server entry in the MCP configuration of an AI tool: `sync` may add and remove that entry only, with these safety rules and an opt-out (`setup --no-memory`), and writes Claude Code's through `claude mcp add-json` and never into `~/.claude.json` itself.
- **Merge** (`install --merge`, `Installer.Merge`). Rendering is deterministic, so the base of a three-way merge is the installed version rendered again, per tool, with the same renderers (`Entry.Targets()`), scope and stamp. Each base file is used only when it hashes to the lock's record (the current model table first, then the empty one for an entry recorded without a table), and a file without a matching base holds both versions whole (`textdiff.Whole`), never a guess. Per path, a table of cases: not edited (or deleted) takes the release. Edited and unchanged in the release keeps yours. Both changed is `textdiff.Merge3` with the labels `yours (edited V)`, `installed V` and `release W` (over 5,000 lines, whole). An edited file the release dropped stays, unmanaged (`MergeResult.Kept`). `findConflicts` runs first and any conflict but an edit refuses the merge as it refuses an install. `--force` with `--merge` is refused, as are folder installs and loadout's own skills, whose old text is not in the binary. Everything happens under `locks.Update`: files are written through the install `tree`, then the entry takes the release's version and the hashes of its own rendered files, so merged files count as edits on the new version and a failed write leaves the lock on the old one (a second run applies each change once). The files left with markers and the labels are a `Merged` record in the sync state (`notice.Service.RecordMerge`), and `notice` shows them as `Unresolved` while `Installer.Marked` still finds a marker line with those labels and the install is still that version. `sync` names `--merge` first in its next steps for holds made only of edits, Pushover's held message names it, and so does the agent's text in the session hooks.
- **Gone.** `update.Registry.Latest` returns `update.ErrGone` for a package the registry no longer has: `registryAdapter.Latest` maps `api.ErrNotFound` from the releases endpoint, and an empty list, to it. A 403 (a team the person left) stays a failure. `syncOne` turns it into `OutcomeGone` ("removed from the registry"): not behind, not a failure, nothing for the notifier, and `remember` drops the install's record. `sync` prints `-` as latest, then `lime/x is no longer on its registry. loadout keeps your files; remove them with: loadout uninstall lime/x --scope user` (a project install adds `--scope project` and the folder to run it in) and exits 0. `sync` never removes the files, since an edited one may be the person's work. `status` and `notices` stay offline and still show the install. Older CLIs keep failing their check with a 404 until updated or uninstalled.
- **Exit code.** `sync` returns an error with `ExitCode() int` (2) when an `auto` install is held back and no check failed. A failed check stays 1 and wins. `runWith` in `cmd/loadout` is the one place that maps errors to codes.

## CLI updates

Plan in `docs/plans/cli-update-notice.md`. When a newer loadout CLI is out, the person using an older one hears about it in one line, with no request of its own and nothing that calls a model.

- **Source of truth.** A registry advertises the release it was built from, only when its build is exactly a clean release tag (`buildinfo.Build.Exact`, `advertised` in `cmd/loadout`), so deploying a tag is how a release reaches people. A commit after a tag, a dirty tree or no tag advertises nothing. `server.MinimumCLI` (none so far) is raised in the commit that drops a fallback an older CLI needs. It only warns.
- **The build.** `buildinfo.Current` reads the ldflags version, else the module version and vcs settings Go stamps into a `go install` build, into a `Build`: the release it is or was built after (a Go pseudo-version `vX.Y.(Z+1)-0.TIME-HASH` is after X.Y.Z), whether it is after it, modified, and its commit. `Behind(v)` is false for an unknown or modified build, so a developer is never told. `MethodOf` (a table) says how it was installed and so how to update it: a download from a registry (`-X main.installMethod=registry`, set only in the CLIs `deploy.sh` builds when `LOADOUT_DOWNLOADS=1`, and the command is `curl -fsSL <registry>/install.sh | sh`, where `Method.For` fills in the address of the registry the notice came from: the one with the newest release, or the one whose minimum this build is under, cut down to scheme and host and refused if it holds anything but host characters), Homebrew (`brew upgrade --cask loadout`), a release download, or a build from source (`git pull && go install ./cmd/loadout` in the person's loadout folder). Machines get `Raw()` (User-Agent, health, log), people `String()`.
- **Downloads from a registry.** With `LOADOUT_DOWNLOADS=1`, `deploy/deploy.sh` also builds the CLI from the checkout (same flags as the registry binary, plus `-X main.installMethod=registry`) for darwin and linux, arm64 and amd64, packs each alone as `loadout_<os>_<arch>.tar.gz` (no version in the name: a deploy replaces them), and writes `checksums.txt` (what `sha256sum` and `shasum -a 256` read), `VERSION` and `deploy/install.sh` with the registry's address put in place of `__LOADOUT_BASE_URL__`. It cannot be combined with `LOADOUT_BINARY` or `LOADOUT_VERSION`, because there is nothing to build then. It uploads one `dl.tar` and `downloads.routes`, swaps `/var/www/loadout-dl` in one step (root-owned, files 0644 and folders 0755, never touching `/var/www/loadout-site`) and installs the routes into `/etc/caddy/loadout.d/`, where the `Caddyfile` imports `*.routes` inside the registry's block ahead of the proxy. A deploy without the variable takes both away. The routes serve `/install.sh` (text/plain) and `/dl/*` (archives as application/gzip) with `Cache-Control: no-cache`, dotfiles hidden and the registry's default policy. `install.sh` is POSIX sh with no `sudo`: it picks the archive for `uname`, refuses a missing or wrong checksum and replaces `loadout` by renaming over it. It downloads over ordinary TLS with curl's default trust store, so the registry needs a certificate the machine already trusts (the `Caddyfile` gets one from Let's Encrypt). There is no certificate route, no CA file option and no step that turns the check off. The registry never runs anything of this: it serves files, and a deployment without the variable publishes none.
- **`loadout update`.** `cli.newUpdateCmd` updates the CLI the way `buildinfo.MethodOf` says it was installed, from what the registries last said (`cliupdate.Status`), and asks no registry itself. A CLI from a registry runs that registry's `install.sh` again (the address is the one the news came from, else the default remote), one from Homebrew runs `brew upgrade --cask loadout`, and a release download or a build from a clone only prints what to do, because loadout cannot do that for the person (`selfUpdating` names the two it may run). The command text is loadout's own, never text a registry sent. `--check` prints the command and runs nothing, `--force` runs it when no newer release is known.
- **Hearing it.** Every client `cli.Deps.newClient` builds has `client.WithCLIAdvice`, which hands the two headers of every response (at most 32 bytes each, unparsed) to `cliupdate.Service.Saw` with the remote's URL. `Saw` keeps parsed versions only, in memory. Anything else is dropped, so nothing a registry sends but two version numbers is ever stored or shown.
- **Remembering it.** `cli.AfterRun`, called by `runWith` after every command (an error too, never after Ctrl-C, never changing the exit code), calls `Finish`, which writes `~/.loadout/cliupdate.yaml` (strict YAML, 0600, atomic, under its own `flock`, a file of its own because older loadouts read the lock and the sync state strictly) only when a registry said something new or its record is a day old. Each registry keeps its latest, minimum and when it was seen. Records older than 30 days are ignored and dropped, at most 16 are kept. A damaged file reads as empty and is started afresh. `Status` reads the file only: the newest release any registry advertised, which one, and the registries whose minimum is above this build.
- **Saying it.** `runWith` detects the audience once (`cliupdate.Detect`: an agent when `CLAUDECODE=1`, `COPILOT_AGENT_SESSION_ID` or `AI_AGENT` is set, a table, else a person when stderr is a terminal, else a script) and `AfterRun` prints `Finish`'s line on stderr after the command's output and its error, so stdout and the exit code never change. A newer release is said at most once a day per version on two clocks kept in the file: the person's (scripts share it) and the agents' (commands they run and the session hook share it). A registry whose minimum is above this build is said every time. `LOADOUT_UPDATE_NOTICE=off` (`config.QuietUpdates`) silences all but that. Nothing is said to an unknown or modified build. Commands marked `quietUpdates` (`status`, `version`, `notices`, `serve`), help, completion and the host's `--data` commands say nothing after themselves.
- **Texts.** `Status.Line`, `Session`, `Footer` and `Version` are built from fixed words, the two parsed versions, the registry's host from the person's own config and the install method's command, so a registry cannot put words in front of a person or an agent. The agent's line starts "loadout, for the agent:" and asks it to tell the user once, with the command, and not to update loadout unless asked. `status` prints `Footer` below its notices, `version` prints `Version` after its first line, `notices` prints the person's line last, and `notices --hook` joins `SessionMessage` to the held-back message (`target.SessionMessage.Join`). None of them asks a registry, and only the hook moves a clock.
- **Pushover.** Only `sync` pushes (see Notifications), once per release on the push clock, and only when this build is behind. A failed push leaves the clock alone so the next run tries again.

## CI and release

- **CI** (`.github/workflows/ci.yml`) runs on every pull request and on `main`: lint, tests with `-race` and govulncheck, a build for each platform the release ships, `scripts/notices.sh --check`, shellcheck over every shell script, `scripts/caddy-adapt.sh` (the Caddyfile adapts without and with the site block), gitleaks over the tree and the history with its default rules, and `scripts/denylist-check.sh`, which only skips unless a maintainer provides the private list. Actions are pinned to commit SHAs with the release named in a comment. The Caddy and gitleaks binaries are pinned by version and checksum. Dependabot (`.github/dependabot.yml`) proposes updates for Go modules and Actions weekly.
- **Release** (`.github/workflows/release.yml`) runs on a `v*` tag: tests, the notices check, then GoReleaser builds archives for Linux, macOS and Windows on amd64 and arm64 with `LICENSE` and the notices, `checksums.txt`, one SPDX SBOM per archive (syft) and the GitHub release. `actions/attest-build-provenance` then attests every file in `checksums.txt`. `gh attestation verify FILE --repo OWNER/REPO` checks a download. The Homebrew cask is not uploaded while `skip_upload` is set in `.goreleaser.yaml`. `make release-snapshot` builds everything locally without publishing (SBOMs only when syft is installed). `deploy.sh` and the Dockerfile verify `checksums.txt` of the release they install.
